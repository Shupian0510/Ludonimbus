# Ludonimbus 存储 v2 与 1.0 路线图（草案 v0.2 · 2026-11-26）

> **背景**：对照 `Ludonimbus规划书`（你的 Obsidian 库）评估了现在的实现。云端以「条目」（key）为单位，快照按「文件在那台电脑上的位置」记录；规划书要的「游戏」和「跨平台」都是事后在每台设备上推算出来的。0.7 的存档库还没发布，线上只有 0.6 的布局，现在改代价最小。
>
> **你的决定（2026-11-25）**
>
> 1. 格式相同的版本**默认自动共用**一条存档历史。开箱即用优先，高级操作留给想自己调的人。（取代 [plan-phase5.md](plan-phase5.md) 5.4 的 D1 = A）
> 2. 存档不通用的版本（旷野之息的 Wii U 版和 Switch 版）**可以在同一张游戏卡上**。（取代 plan-phase5 5.5 里「只有存档通用的版本才合成一个游戏」）游戏卡和游戏页的界面跟存储、游戏库一起重新设计。
> 3. 规则库**留在主仓库**。
> 4. 1.0 **不需要** PSP 和 macOS，**需要**接管 Steam 云存档：可以把全部存档、或者 Steam 里的部分游戏交给 Ludonimbus。还要能把一个游戏标成**分设备存储**，同一个 Steam 账号、不同的人在不同设备上玩时不冲突。
>
> **原则**：功能容易理解、安全，用户可以放心把存档都交给软件。
>
> **你的补充（2026-11-26）**
>
> 5. 游戏页要能管理这个游戏在云端的所有存档，其中一份是「当前启用的」。把别的存档拖过去就切换：同一平台的旧版本、别的平台的存档（自动转换）、发到 Switch。自动保存的版本不列出来（照旧保留）；手动存的「存档实例」有名字、可以随时切回去；每个平台最新的一份也列出来。
> 6. 云盘可能很慢、不稳定，存储结构要保证上传效率。方案要简洁、经过设计，并且留好扩展，因为以后的功能都建在它上面。
> 7. 几个平台**默认共用一个当前进度**：在 Xbox 版玩完，Steam 版启动时自动接上。让某个平台各走各的是可选项（改成独立，第 7 节）。
> 8. 界面：**现有的游戏页结构保留**，第 5 条的拖动只是一个想法，不必照做。要的是「切换和转换存档、现在用的是哪一份、多设备」这些事通过自然的交互完成，不藏得很深。文字要少：功能说明放进悬停的问号，关键提示（比如覆盖）用弹窗。不要多余的动效，软件主打轻量。整套界面的重构单独算一个大版本；新功能实现时先把交互想好。名字可以改（「存档实例」在本文里改叫「保留的存档」）。
>
> **v0.2 相对 v0.1 的变化**：云端文件分四类（3.1）；快照拆成清单和内容包，大存档只上传变化的文件（3.4）；保留的存档（3.7）；索引（3.8）；扩展规则（3.9）；保留策略、等待时间、每个操作的开销（5.4 到 5.6）；「设为当前」一个动作（第 9 节）；界面规则和游戏页只改的两处（第 10 节）。
>
> **发布方式（2026-11-26 定）**：不按版本一个个发。0.7 不单独发布；存储 v2、接管 Steam 云存档、界面重构一起做完，直接发 1.0。先做什么由实现时安排（第 14 节）。

| 部分 | 一句话 |
|---|---|
| 模型 | 云端三层：游戏、存档线、快照。本机两样：安装、绑定 |
| 云端文件 | 四类：不可变的（内容包、清单）、单设备写的、可合并的小记录、可重建的索引。正确性不依赖任何会被改写的文件 |
| 快照 | 一份清单加内容包，按规范路径存，不带任何设备上的位置。大存档只上传变化的文件 |
| 同步 | 用版本向量判定最新版本和分叉，不看时钟 |
| 开销 | 每个操作的请求数固定，和版本数量无关。启动前没有新版本时只等一次请求；退出后先存本机，再上传 |
| 自动共用 | 分三档：直接共用、问一次、各自一条线；写前留恢复前版本，可以一键撤回 |
| 独立存档 | 同一格式下再开一条只属于某台设备的存档线 |
| Steam 游戏 | 三种状态：Steam 管、只备份、Ludonimbus 管 |
| 界面 | 游戏页结构不变。和存档有关的只改版本条和「存档」页签：当前的一份、各平台最新的一份、保留的存档在上，自动存档收起；一个主操作「设为当前」。其余界面按同一套规则一起重做 |
| 迁移 | 不搬文件：新记录引用旧文件夹 |

## 1. 现在的问题

| 问题 | 在哪里 | 后果 |
|---|---|---|
| 云端没有「游戏」这个实体 | `savelib::families`：每台设备用并查集按 `ids` 算，代表是「最小的 key」 | 加一个条目，游戏的代表就可能变；改名、合并要逐条目改；Switch、Deck 客户端都得重算一遍 |
| key 是名字的 slug，只查本机是否重复 | `games::unique_key` | 两台设备各自添加：名字一样就混进同一条历史（哪怕一个是 Steam 版一个是 Xbox 版），不一样就成了两个版本 |
| 快照按位置记录 | `spec::tokenize`、应用的 `folder_to_pattern`：认不出的位置记成 `drive-d/…`；Xbox 容器原样存进快照 | 换一台电脑会恢复到同一个绝对路径；跨版本只能靠 `transfer.rs` 里的对齐逻辑去猜 |
| 最新版本按时间戳判定 | `sync::mainline_head` 取 `created_at` 最大的 | 见下面的例子 |
| 每个版本各一条历史 | 跨版本靠手动「应用到…」和 `savelib::newer_version` 按时间比较 | 做不到「无论在何处启动都能继续」 |
| 时长、成就、截图、封面挂在条目上 | `games/<key>/playtime/…` 等 | 「跨平台总时长」要另外加总 |
| 云端逻辑有两套实现 | `cloud/gdrive.rs` 自己实现 `CloudProvider`，其余走 `cloud/repo.rs` | 每次改布局要写两遍 |
| 云端没有布局版本号 | 没有任何标记 | 以后换布局，旧版本会照旧往里写 |
| 规则分散在 5 种文件里 | `adapters/` 下的 builtin、emulators、recomplauncher、xbox-saves、cross-saves，加 `achievements/` | 一个游戏的信息散在几处，贡献者不知道改哪里 |

**时间戳的例子**（按代码推演，没有写测试复现）：A 和 B 都同步到版本 P。A 离线玩了一局，新版本 S_a 进了待上传队列；之后 B 在线玩了一局，上传 S_b（父版本 P）。A 联网后传上 S_a，这时最新版本按时间是 S_b；A 本机的存档等于「上次同步的 S_a」，被判成「本机没变、云端有新版本」，直接拉取 S_b。A 的那一局还在版本历史里，没有丢，但没有问过用户。S_a 和 S_b 的父版本都是 P，这本来是一次分叉。同样的原因，一台时钟快了的设备传上去的版本会一直是「最新」，别的设备的新进度会被拉回去。

**保留的**：不可变的 zip 快照（网页上能手动取回）、`Store` 抽象和各云盘实现、离线队列、恢复前版本、`{根目录}/相对路径` 的写法、`{nxsave-…}` 这种按设备解析的根、Xbox 容器读写、游戏本体备份的切块。

## 2. 模型

**云端（所有设备共用）**

| 概念 | 是什么 | 例子 |
|---|---|---|
| **游戏** | 用户心里的那个游戏，一张游戏卡。有固定的 id 和各平台的身份 | 星露谷物语；旷野之息 |
| **存档线** | 一组能互相直接读取的存档，共用一条版本历史。一个游戏有一条或几条 | 星露谷：一条（PC、Xbox、Switch 通用）。旷野之息：`switch` 一条、`wiiu` 一条 |
| **快照** | 存档线上的一个版本：一份清单（有哪些文件）加内容包（文件本身，zip）。内容按规范路径存 | `saves/Farm_1/SaveGameInfo` |
| **保留的存档** | 用户要一直留着的快照，可以起名字。不会被清理，显示在游戏页上 | 「通关前」 |

**本机（每台设备自己的）**

| 概念 | 是什么 | 例子 |
|---|---|---|
| **安装** | 这台设备上某个游戏的某个平台版本：程序、启动参数、Steam 快捷方式、跟哪条存档线 | 这台电脑上的星露谷 Steam 版 |
| **绑定** | 这个安装把规范路径对应到哪个实际文件夹、用哪种编解码 | `saves` ↔ `%APPDATA%\StardewValley\Saves`，普通文件 |

要点：**「是什么存档」记在云端，「存档在这台设备的哪里」只记在本机**。跨平台不再是一次次的转移，而是几个安装绑定到同一条线；格式转换是绑定上的编解码。

**例子：星露谷在三个地方**

```
云端   library/stardew-valley-7k3f.json        游戏记录，一条存档线 main
       games/stardew-valley-7k3f/saves/main/01J….json     清单
       games/stardew-valley-7k3f/packs/01J….zip           内容包
            files/saves/Farm_1/Farm_1
            files/saves/Farm_1/SaveGameInfo

电脑   安装 Steam 版   绑定  saves ↔ {appdata}/StardewValley/Saves            普通文件
       安装 Xbox 版    绑定  saves ↔ {localappdata}/Packages/…/wgs/<用户>_<标题>   Xbox 容器
Switch 安装（经电脑）   绑定  saves ↔ {nxsave-0100e65002bb8000}                Switch 存档
```

三个安装算出来的内容哈希相同时就是「已同步」。在 Switch 上玩完，电脑上启动 Steam 版前照常拉取，不需要「应用到…」。

## 3. 云端布局

### 3.1 目录

```
Ludonimbus/
├─ format.json                          布局版本和用到的特性（3.2）
├─ devices/<设备 id>.json                设备信息 + 这台设备有哪些安装（3.5）
├─ library/<游戏 id>.json                游戏记录（3.3）。平铺在一个文件夹里
└─ games/<游戏 id>/
   ├─ packs/<内容包 id>.zip                     存档内容（3.4）。这个游戏的所有存档线共用
   ├─ saves/<存档线 id>/<ULID>.json             清单 = 一个快照（3.4）
   ├─ saves/<存档线 id>/<ULID>.pin.json         保留的存档（3.7）
   ├─ saves/<存档线 id>/index.json              索引（3.8）
   ├─ saves/<存档线 id>/trash/<ULID>.json       最近删除（记录的格式和现在一样；旧文件夹里的版本仍记在 `games/<key>/trash/`）
   ├─ playtime/<设备 id>.json
   ├─ achievements/…   screenshots/<设备 id>/…   art/…
   └─ （0.6 留下的）game.json、snapshots/       旧文件原样留着（第 12 节）
gamebackup/…                             游戏本体备份，不变
```

**所有文件分四类。** 这些云盘共有的能力只有列目录、读、写、删，没有「没被别人改过才写入」。所以正确性只能建立在「文件存在与否」和不可变的内容上，不能依赖任何会被改写的文件。

| 类型 | 有哪些 | 规则 |
|---|---|---|
| **不可变** | 内容包、清单 | 写一次，不再改。两台设备同时写不会互相覆盖（名字不同）；本机读过一次就永久缓存 |
| **单设备写** | `devices/<设备>.json`、`playtime/<设备>.json`、`screenshots/<设备>/` | 只有那台设备写，没有并发 |
| **可合并的小记录** | `library/<游戏>.json`、`<ULID>.pin.json`、`trash/<ULID>.json` | 很少改，写前重读。能做成「一个事实一个文件」的就这么做：文件在就是有，删了就是没有 |
| **可重建的索引** | `index.json` | 只是缓存。丢了、旧了、被别的设备覆盖了，都能从清单重建；和目录列表不一致时以目录为准 |

- **没有「指向最新版本」的文件。** 最新版本由清单里的版本向量算出来（5.1）。这种指针文件会被两台设备互相覆盖。
- 以后新增的任何数据都要归到这四类之一（3.9）。

- **游戏 id**：新游戏是「名字的 slug + 4 位随机字符」（`stardew-valley-7k3f`），建的时候不用查云端也不会撞。从 0.6 迁移来的游戏沿用旧 key，文件夹不用改名。
- **游戏记录平铺在 `library/`**：列一次目录就拿到所有记录的变化标记，只读有变化的（`Repo::read_tagged` 现有的缓存）。现在 `list_games` 是每个游戏读一次 `game.json`。
- **Google Drive 并入通用实现**：`GoogleDrive` 已经实现了 `Store`，去掉它自己的 `CloudProvider` 实现，云端逻辑只留 `Repo` 一套。待验证：首次列版本的耗时（第 15 节）。

### 3.2 `format.json`

```json
{ "layout": 2, "minApp": "1.0.0", "requires": [], "migratedAt": "2026-…", "migratedBy": "d-01j…" }
```

- 没有这个文件 = 布局 1（0.6）。
- 程序记着自己认识的最高布局。云端的布局更高时：**只读**，不上传、不删除，提示更新。
- `requires`：这个云端用到的、不认识就不能写的特性（3.9）。有不认识的项时同样只读。这样以后加特性不用再升布局号。
- 发布过的只有 0.6（布局 1），下一个发布的是 1.0（布局 2）。0.6 不认识这个文件，处理办法见 12.3。1.0 之后再换布局或加特性，靠它拦住旧版本。

### 3.3 游戏记录

```json
{
  "id": "stardew-valley-7k3f",
  "name": "Stardew Valley",
  "ids": ["steam:413150", "nx:0100E65002BB8000", "ludusavi:stardew valley",
          "xbox:ConcernedApe.StardewValleyPC", "rule:stardew-valley"],
  "rule": "stardew-valley",
  "folders": ["stardew-valley-7k3f"],
  "lines": [
    { "id": "main", "format": "rule:stardew-valley", "scope": "shared",
      "path": "games/stardew-valley-7k3f/saves/main" },
    { "id": "solo-9d2k", "format": "rule:stardew-valley", "scope": "independent",
      "name": "孩子的电脑", "path": "games/stardew-valley-7k3f/saves/solo-9d2k" }
  ],
  "tags": ["finished"], "notes": "",
  "createdAt": "2026-…", "rev": 12, "updatedAt": "2026-…", "updatedBy": "d-01j…"
}
```

- `ids`：这个游戏在各平台的身份。**强身份**：`steam:`、`nx:`、`xbox:`、`gog:`、`epic:`、`ludusavi:`、`ra:`（RetroAchievements）、各主机的标题 id（`wiiu:`、`ps4:`…）、`rule:`。**弱身份**：`name:<去掉符号的小写名字>`。
- `lines[].format`：这条线的规范路径是哪一套（4.2）。
- `lines[].def`：这条线存的是哪些文件，是「去哪儿找存档」的指纹。Switch 游戏是标题 id（`nx:0100E65002BB8000`，本机和各模拟器都一样）；其他的由规则、存档路径（不分顺序、大小写、斜杠方向）、Ludusavi 标题、是不是 Xbox 应用的版本算出来。具名文件夹在各台设备上指向哪里不算在内。**同一格式、`def` 相同的两条线存的是同样的文件，可以共用一份历史**；没有这一项就是不知道，不会被当成相同（第 6 节）。
- `lines[].path`：新快照的清单写到哪里（内容包写到 `folders` 里第一个文件夹的 `packs/`，读的时候在所有文件夹的 `packs/` 里找）。`lines[].also`：只读的其他位置，例如迁移前的 `games/<key>/snapshots`（布局 1），或者合并进来的另一条线。**存档线自己记路径，所以合并游戏、迁移都不用搬文件。**
- `folders`：这个游戏在 `games/` 下的数据文件夹，第一个用来写，其余只读。时长、成就、截图、封面读所有文件夹（合并过的游戏有几个）。
- **只放很少改动、和设备无关的内容。** 和设备有关的都在各设备自己的文件里（3.5 和 `playtime/<设备>.json` 等），每台设备只写自己的文件。
- **两台设备同时改同一条记录**：没有条件写入，后写的覆盖先写的。减轻的办法：写之前重新读一次并合并（`ids`、`lines`、`folders`、`tags` 取并集，`rev` 加一），只有 `name`、`notes` 这类单值可能丢一次改动。
- **两台设备各自建了同一个游戏**（都离线，或者同时）：刷新时发现两条记录有相同的强身份，自动合并。建得早的留下，另一条写上 `"mergedInto": "<id>"`，它的存档线和文件夹并进留下的那条。合并后两条共用的线格式相同、`def` 也相同时，并成一条（一条进 `also`），两边各有进度就是一次普通的分叉，照 5.2 问用户；`def` 不同的各留一条线。
- **同名不同游戏被合到一张卡**（只靠弱身份合并的）：游戏页里「拆开」。因为只是同一张卡、存档线各是各的，合错不会动到存档。

### 3.4 快照：清单和内容包

一个快照 = 一份清单（`saves/<线>/<ULID>.json`）加它用到的内容包（`packs/*.zip`）。

```json
{
  "v": 2, "id": "01JF…", "game": "stardew-valley-7k3f", "line": "main",
  "vv": { "d-01ja…": 12, "d-01jb…": 4 },
  "parent": "01JE…",
  "deviceId": "d-01ja…", "deviceName": "Desktop",
  "platform": "steam", "createdAt": "2026-…", "trigger": "auto-exit",
  "contentHash": "…", "totalSize": 1234,
  "files": [
    { "path": "saves/Farm_1/Farm_1", "size": 5, "hash": "…", "mtime": 0 },
    { "path": "saves/Farm_1/SaveGameInfo", "size": 1, "hash": "…", "mtime": 0, "in": "01JE…" }
  ],
  "gameVersion": "1.6.15", "installedVersion": "1.6.15",
  "info": { "title": "Farm_1", "detail": "第 2 年 夏 12 日" },
  "origin": { "game": "…", "line": "…", "snapshot": "01J…", "how": "copy" },
  "appVersion": "1.0.0"
}
```

- `vv`：版本向量（5.1）。`parent` 留着只用来显示。
- `files[].in`：这个文件的内容在哪个内容包里。不写 = 在和清单同名的包里（`packs/<id>.zip`）。
- `roots`（那台设备上的绝对路径）不再是清单的字段。绑定（4.2）做完之前，它和创建时写的备注（`comment`）暂时作为扩展字段（3.9）跟着清单走：把存档应用到游戏的另一个版本时还要读 `roots`。
- `info`：存档摘要，规则说得出怎么读时才有（第 11 节）。
- `origin`：由恢复、复制或转换产生的版本记下来源（第 9 节）。
- `comment`、`locked` 拿掉，换成保留的存档（3.7）。清单写完就不再改。

**内容包**是普通的 zip：`files/<规范路径>`，加一份 `snapshot.json`（写这个包时的清单副本，说明它是什么）。网页上能下载、能直接解压。

- **0.6 的快照就是「所有文件都在自己的包里」的清单**，不需要转换，读的代码是同一套。
- **清单最后写，作为提交标记**（和现在一样：先传 zip，再写 json）。只有包没有清单 = 没传完，下次接着传或者过期清掉。

**怎么写，按存档大小分**

| 情况 | 怎么写 |
|---|---|
| 存档总共不超过 16 MB | **每个版本一个完整的包，和现在一模一样。** 恢复、复制产生的版本也传自己的包。云端最新的 zip 就是最新的进度，不需要别的文件就能手动取回 |
| 更大 | 新包里只放相对「本机上次同步的那个版本」有变化的文件；没变的文件用 `in` 指向原来的包。恢复、复制只写一份清单，不传内容 |
| 一次要传的内容超过 64 MB | 分成几个包（`<id>.zip`、`<id>-2.zip`…），每个包里是完整的文件。传到一半断了，下次从没传完的那个包接着传 |

- 只有路径和内容都相同才算没变。改了名的文件当新文件重传（存档里很少见）。
- **你这台电脑上的情况**（2026-11-26，读了本机缓存的清单）：5 个游戏，最大的 6.3 MB（26 个文件），都在第一档。对这些游戏，慢的不是传多少字节，而是请求次数（3.8、5.6）。增量上传是给大存档准备的：一个文件夹里攒了几十个存档文件的游戏、沙盒游戏的世界、模拟器的整套存档。
- 16 MB、64 MB 是**写的一方的策略**，不是格式的一部分。读的一方只需要认识 `in`。以后调数值、换策略都不动格式，旧版本也读得了。

**大存档才用得上的规则**

- **内容包按游戏放，不按存档线放。** 所以把一个版本复制到另一条线、从共用改成独立，都只是多一份清单。
- **什么时候删包**：没有任何清单引用它（最近删除里的也算）。删清单的设备顺手算出只有这份清单在用的包，一起删。小存档的包只被自己的清单引用，跟着清单删，和现在一样。
- **整理**：有的包里大部分文件已经被后来的版本换掉了，恢复时却要整包下载。一个版本用到的包总大小超过它实际内容的 2 倍时，上传时顺带把最浪费的那个包里还在用的文件重传一遍。顺带的量有上限（不超过这次本来要传的量，至少 16 MB），不会突然要重传整个存档。
- **引用的包被删了怎么办**（两台设备同时一个写、一个删）。三条规则，哪一条都不依赖时钟对得准：
  1. 写的一方只引用自己上次同步的版本用到的包（保留策略为每台设备留着它，5.4）；清单写完后再列一次 `packs/` 核对，缺了就立刻补传一个完整的包。
  2. 删的一方删包之前重新列一次清单，仍然没人引用才删。
  3. 读的一方下载时发现缺包：不动本机存档，报告这个版本不完整，等写它的设备补传。
- **单个很大的文件每次只改一小块**（几百 MB 的世界文件、记忆卡镜像）：按文件去重帮不上。留了扩展位置（3.9）：`files[].chunks`，用游戏本体备份已经有的按内容切块（[plan-game-backup.md](plan-game-backup.md) 2.2）。1.0 不做。

### 3.5 设备

`devices/<设备 id>.json` 在现有内容上加：认识的最高布局、这台设备的安装列表（游戏、存档线和它的文件夹、平台、上次同步到哪个版本、什么时候）。别的设备据此显示「在哪些设备上玩过、装着」，也据此判断旧版本设备还在不在用（12.3）；清理时按存档线的文件夹找出每台设备上次同步到的版本（5.4）。

### 3.6 时长、成就、截图、封面、游戏本体

时长、成就、截图、封面都按**游戏**存，不按某台设备上的 key 存。规则只在一处（`cloud/gamedata.rs`），这四个模块都问它。

- **读**：游戏记录的所有文件夹（`folders`，按记录里的顺序）。一个游戏的总时长、解锁、截图就是这几个文件夹里的全部。别的设备的文件照旧只在变化标记变了时才重新读。
- **写**：什么都不搬，也不从一个文件夹复制到另一个。
  - 记录里有一个文件夹和这个安装的 key 同名：写在那里，文件名和 0.6 一样（`playtime/<设备>.json`、`achievements/<设备>.json`、`screenshots/<设备>/`）。原来的安装照旧写在原来的地方，还在用 0.6 的设备（只认识 `games/<自己的 key>/…`）照样看得到。
  - 否则（这个安装接着用别的 key 建的卡，条目里有 `record`，第 6 节）：写在记录的第一个文件夹，按设备分的文件名里带上 key：`<设备>~<key>.json`，截图的设备文件夹是 `<设备>~<key>/`。同一台设备上同一个游戏的两个安装不会写同一个文件，自己的 key 下也不会多出一个文件夹（那会在云端显示成又一个游戏）。
- **按设备分的文件**，每个是一个安装的：设备是文件里写的，没写就是名字里 `~` 前面的部分；安装是 `~` 后面的部分，没有 `~` 就是文件所在的文件夹。读的一方把同一个安装的几个文件合并（文件夹的顺序变过，同一个安装可能写过两处；时长按开始时间每段只算一次），不同安装相加，再按设备分组显示。这台设备上同一个游戏的另一个安装也算这台设备的时间。截图不会下载到同一台设备的另一个安装的 Steam 文件夹里（它们本来就在这台电脑上）。
- **0.6 的设备看到什么**：它列这个文件夹，看到 `<设备>~<key>.json` 不是自己的文件名，就当作另一台设备的文件，总时长仍然是对的。
- **每个游戏一份的**（封面的 `art.json` 和图片、成就定义 `schema.json`）：从按顺序第一个有的文件夹读。封面按种类找：每种图取第一个在 `art.json` 里有它的文件夹。这台设备上传到自己写的那个文件夹；从别的文件夹拿到的封面和成就定义不传回去（那等于复制）。
- **在哪些文件夹**：问 `Cloud::game_folders`（就是 `Cloud::place` 的 `folders`）。这台设备同步过这个游戏后不用请求，否则列一次 `library/`（同一个 `Cloud` 一分钟内不重列）。没有云盘、离线时，本机记录和显示照旧；写到哪里在真正上传时才决定。只有存储、拿不到 `Cloud` 的地方（托盘的截图同步）用本机上次记下的文件夹；没有记下时，接着别的卡的游戏用那张卡（`record`）的文件夹，其余的用 key 自己的文件夹，和 0.6 一样。
- **开销**：记录只有一个文件夹、并且和 key 同名（几乎所有游戏）时，请求和以前完全一样。每多一个文件夹，每种数据多列一次目录（按设备分的文件）或多读一次（每个游戏一份的）。
- **每段游戏时间**多记 `platform`（和存档清单的写法一样：`pc`、`emu:<规则>`、`recomp:<规则>`）和 `line`（这台设备上这个游戏跟的存档线）。以前的场次没有这两项，照常读，原样保留。总时长是所有设备、所有平台的和；按平台的时长（`playtime::Summary::platforms`）已经算出来，界面还没做。
- 成就按来源存（RetroAchievements 的游戏 id、PS 奖杯的 NPWR 编号），同一个游戏在不同模拟器里是同一份。**还没做**：现在仍按游戏的文件夹存。
- 游戏本体备份的布局不变（`gamebackup/games/<文件夹>/…`），按 `folders` 找。**还没做**：现在仍按每个安装的 key 存。

### 3.7 保留的存档

`saves/<线>/<快照 id>.pin.json`：

```json
{ "name": "通关前", "note": "", "createdAt": "2026-…", "deviceId": "d-01ja…" }
```

- 这个文件在，这个快照就一直保留，并且显示在游戏页「存档」页签的上半部分（10.2）。`name` 可以空着。
- 两个入口：操作栏里现有的「备份当前存档」（`trigger: manual`，存的时候同时写一个 pin）；任何一份自动存档上的「保留」。
- 「备份当前存档」时这条线上已经有内容相同的版本：不再上传，直接保留那个版本并起名。本机存档不是这条线接下来该有的版本时（云端有更新的，或者有冲突还没处理），这份备份放在历史旁边，不成为最新版本：备份不替用户做决定。
- **「保留」只看这个文件在不在。** 0.6 留下的 `locked` 和手动备份，迁移时各补一个 pin（12.1）；之后旧文件里的 `locked` 只是历史。旧版本上不属于保留存档的备注（`comment`）不丢，跟着快照进索引，界面照常显示。
- 起名、改名 = 重写这个文件。取消保留 = 删掉这个文件，快照回到普通的自动存档，按保留策略处理。
- 现在的「锁定」和「备注」（`locked`、`comment`，`sync::set_snapshot_flags`）合成这一个。它们要改写快照的元数据；换成单独的文件后清单就不用再改了。

### 3.8 索引

每条存档线一个 `index.json`：这条线上每个快照的摘要（清单去掉文件列表，加上它用到的包和保留时起的名字）。

```json
{ "v": 1, "updatedAt": "2026-…", "updatedBy": "d-01ja…",
  "snapshots": [
    { "id": "01JF…", "vv": { "d-01ja…": 12 }, "deviceId": "d-01ja…", "deviceName": "Desktop",
      "platform": "steam", "createdAt": "2026-…", "trigger": "auto-exit",
      "contentHash": "…", "totalSize": 1234, "packs": ["01JF…", "01JE…"],
      "info": { "title": "Farm_1" }, "pin": "通关前" } ] }
```

- **为什么要它**：现在列版本是每个版本读一次 `.json`（`Repo::list_snapshots`，读过的有本机缓存）。新设备第一次打开一个有 50 个版本的游戏要 50 次请求，夸克上每次 1 到 7 秒。在另一台设备上玩了一周再回来，启动前也要把这一周的新版本逐个读一遍。
- **有了它**：列一次目录；目录里 `index.json` 的变化标记变了，再读它一次。**两次请求，和版本数量无关。**
- 它只是缓存，不决定任何事：

| 情况 | 怎么办 |
|---|---|
| 目录里有清单，索引里没有 | 直接读那份清单（多一次请求）。下一个写的设备会把它补进索引 |
| 索引里有，目录里没有 | 忽略 |
| 两台设备同时写索引，一边的改动被盖掉 | 就是上面第一种情况 |
| 索引丢了、坏了 | 从清单重建 |

- 迁移过来的旧文件夹里的快照也收进索引，旧版本同样是两次请求。
- 删包时要知道每个清单用了哪些包，也从这里读，不用逐个读清单。

### 3.9 扩展规则

存储是其他功能的基础。以后加东西按这几条来，不用再换布局：

| 规则 | 说明 |
|---|---|
| 不认识的字段原样保留 | 读一条记录时把不认识的字段留着，写回去时带上。新版本加的字段不会被旧版本抹掉 |
| 清单的外层字段固定 | `v`、`id`、`line`、`vv`、`side`、`deviceId`、`createdAt`、`requires` 的含义不再变。旧版本看不懂一份新清单的内容，也能算出谁是最新版本、有没有分叉。`side: true` 表示这份快照放在历史旁边、永远不算最新版本（恢复前留的那份、冲突里没选的那一边）；以后新增的这类快照只要带上它，旧版本就不会把它当成最新 |
| 按特性声明 | 清单里的 `requires: ["chunks"]`：不认识其中任何一项的程序不恢复这个版本（提示更新），其他版本照常用。`format.json` 里的 `requires`：不认识的程序对整个云端只读 |
| 新数据归到四类文件之一（3.1） | 新的每游戏数据放在 `games/<游戏>/<种类>/` 下，要么按设备分文件，要么不可变。不往游戏记录里放会经常改的内容 |
| 只用列目录、读、写、删 | 不依赖任何一种云盘特有的能力。新增一种云盘只要实现 `Store`；Switch 上的 C++ 客户端照同样的规则就能直接读写 |
| 策略不进格式 | 什么时候传完整的包、保留多少个版本、等几秒，是程序的行为，可以随版本改 |

已经能想到的扩展，各自落在哪里：

| 以后的功能 | 怎么加 | 动不动布局 |
|---|---|---|
| 大文件按块去重 | `files[].chunks` 加 `games/<游戏>/chunks/`，清单 `requires: ["chunks"]` | 不动 |
| 端到端加密 | 内容包和清单多一种编码，`format.json` 的 `requires: ["enc1"]`，密钥只在设备上 | 不动 |
| 新的存档格式（记忆卡、3DS…） | 新的编解码（4.2） | 不动 |
| 新的平台和客户端（macOS、PSP、Switch 直连云盘） | 新的 `platform` 值和绑定 | 不动 |
| 新的每游戏数据（设置、mod 列表、录像） | `games/<游戏>/<种类>/…` | 不动 |
| 跨版本转换 | 规则里的转换器（第 9 节），产生的是普通快照 | 不动 |

## 4. 本机

### 4.1 安装

`config.json` 里的 `games` 换成 `installs`（迁移见 12.1）：

```json
{
  "id": "stardew",
  "game": "stardew-valley-7k3f", "line": "main",
  "platform": "steam",
  "name": "Stardew Valley",
  "exe": "…", "args": "", "workDir": null, "install": null, "steam": { … },
  "adapter": null,
  "bind": [ { "canon": "saves", "local": "{appdata}/StardewValley/Saves", "codec": "files" } ],
  "sync": "auto"
}
```

- `id` 是本机 id，就是 Steam 快捷方式里的 `--game <id>`。迁移时等于旧 key，**已经加进 Steam 的快捷方式不用改**。
- `platform`：`steam`、`epic`、`gog`、`xbox`、`pc`（其他 PC 版）、`emu:<规则>`、`recomp:<规则>`、`console:switch`。
- `bind`：规则给得出来时不存（运行时从规则得到），用户改过或者是确认过的推断结果才存。
- `sync`：`auto`、`manual`（不自动同步）、`backup-only`（只备份，第 8 节）、`off`。
- **现在的做法**：`games` 和 `GameEntry` 还没有改名，本机 id 就是 key。条目里已经有 `line`（跟哪条线，第 7 节）和 `record`（属于云端哪条游戏记录，第 6 节；没有这一项就是和 key 同名的那条）。`platform`、`bind`、`sync` 等绑定做的时候一起加。

### 4.2 绑定、规范路径、编解码

**规范路径是哪一套，由存档线的 `format` 决定：**

| `format` | 规范路径 | 用在哪里 |
|---|---|---|
| `pc` | `<可移植的根>/<相对路径>`：`appdata`、`localappdata`、`documents`、`home`、`install`、新增的 `steamuser`（`<Steam>/userdata/<账号>`），以及具名挂载点 | 没有规则的 PC 游戏。就是现在的写法去掉 `drive-x` |
| `nx` | `nxsave-<标题 id>/…`、`nxdevice-<标题 id>/…` | Switch 本机、Ryujinx、yuzu 系。和现在一样 |
| `adapter:<规则>` | 规则自己的根（`data/…`、`mlc/…`、`emu/…`） | 重编译、其他模拟器。和现在一样 |
| `rule:<id>` | 规则定义的挂载点（`saves/…`） | 有跨平台规则的游戏 |

- **认不出的位置**（现在记成 `drive-d/…`）：建一个具名挂载点（`m1`），云端只记名字，绝对路径记在本机的绑定里。别的设备第一次同步这个游戏时问一次「这个文件夹在这台设备的哪里」。
- **绑定**是一组对应关系：`{ canon, local, codec, files }`。`canon` 是规范路径的前缀，`local` 是这台设备上的文件夹（可以用根目录模板），`files` 是哪些文件算存档。同平台、同规则时就是恒等的，不用写。
- **编解码**（`codec`）：把设备上的东西读成规范文件，再写回去。

| 编解码 | 做什么 | 现有代码 |
|---|---|---|
| `files` | 普通文件，按前缀对应 | `snapshot::scan` / `apply` |
| `wgs` | Xbox 存档容器，按命名规则还原文件名；写入只替换已有的存档位 | `wgs.rs`、`xboxsaves.rs` |
| `nx` | Switch 存档：Ryujinx 查存档编号（没有就新建），yuzu 系拼固定路径 | `switch.rs`、`emulators::prepare_restore` |
| 以后 | GameCube 记忆卡、3DS 路径里的机器 id、字节序不同的游戏 | — |

- **一种格式升级成规则**：一个游戏先按 `pc` 存了一段时间，之后有了规则（`rule:<id>`）。旧快照不用重写，读的时候按规则里 PC 的位置把路径换成规范路径（现在 `crosssaves::relative` 做的事）。
- **内容哈希按规范路径和内容算**，所以 Steam 版和 Xbox 版存的是同样的内容时哈希相同。

### 4.3 状态

`state.json` 按安装记：上次同步的版本 id、内容哈希、版本向量，本设备在这条线上的计数，冲突，待上传。计数丢了可以从云端的快照里找回（取所有快照里本设备分量的最大值）。

读过的清单在本机永久缓存（它们不会变）。上次同步的那份是下次增量上传的基准。

## 5. 同步

### 5.1 版本向量

每个快照带一个 `vv`：`{设备 id: 计数}`，意思是「这个版本包含了每台设备到第几次为止的修改」。

- 上传时：取本机存档所基于的那个版本的 `vv`，把本设备的计数加一。
- A **包含** B：A 的每个分量都不小于 B 的。
- **最新版本** = 主线快照里不被任何其他快照包含的那些。只有一个：它就是最新版本。有几个：分叉。
- 不看时钟，`createdAt` 只用来显示。保留策略删掉中间的版本不影响判断（只靠 `parent` 指针的话，删掉中间版本会让它的父版本看起来像另一个头）。

第 1 节的例子在这里：S_a = `{A: 6, B: 3}`，S_b = `{A: 5, B: 4}`，互不包含，是分叉，会问用户。

### 5.2 判定表

和现在的表一样（[plan-phase1.md](plan-phase1.md) 5.1），「云端自上次同步后有没有新版本」改成比较向量：

| 本机存档 | 云端 | 动作 |
|---|---|---|
| 没变 | 最新版本就是上次同步的 | 直接启动 |
| 没变 | 一个最新版本，包含上次同步的 | 拉取（先留恢复前版本） |
| 变了 | 最新版本就是上次同步的 | 上传 |
| 变了 | 一个最新版本，不是上次同步的 | 冲突，问用户 |
| 任意 | 几个最新版本（分叉） | 内容哈希都相同：不算冲突。否则问用户选哪一个（本机变了的话本机也是一个选项） |
| 没有存档 | 有版本 | 拉取 |

解决冲突时上传的版本，`vv` 取所有头的逐分量最大值再加一，分叉就此合上。落选的各方照旧留着（`conflict-keep`），什么都不删。

### 5.3 旧快照

布局 1 的快照没有 `vv`。读的时候给主线上的每一个合成 `{legacy:<旧 key>: 创建时间的毫秒数}`，也就是保持 0.6 自己用的先后（它按 `createdAt` 认最新）。第一个 v2 快照基于其中最新的那个。

**每个旧文件夹各算各的。** 只有同一个旧文件夹里的快照才是同一条历史。两个旧 key 以后并成一条线时，两边最新的版本互不包含，是一次分叉，会问用户；不会因为一边的时间晚就悄悄盖掉另一边。

用时间而不用序号：0.6 的设备清掉一个旧版本后，序号会整体前移，它之后上传的版本就可能拿到一个已经被 v2 的新版本「包含」的序号，这次分叉就看不出来了。时间不会变。

### 5.4 保留策略

每条存档线上一直保留：

| 保留什么 | 为什么 |
|---|---|
| 最新版本（分叉时每一个头） | 当前进度 |
| 保留的存档 | 用户要留的（3.7） |
| 每个平台最新的一份 | 游戏页的「存档」页签要显示（10.2） |
| 每台设备上次同步到的那个版本 | 那台设备下次增量上传的基准；出现分叉时也能说清两边各改了什么。设备记录里有（3.5）。一台设备 90 天没出现就不再为它保留 |
| 其余的自动版本 | 和现在一样：最近 20 个，加 30 天内每天一个（设置里可以改） |

- 恢复前版本、冲突里落选的版本的保留方式不变：和其他自动版本一起算在那 20 个和每天一个里。
- **保留策略不删 0.6 旧文件夹里的任何快照。** 0.6 把旧文件夹里最新的那个当作当前进度；删掉它，还在用 0.6 的设备会把存档退回到前一个。旧文件夹里留下的数量有上限（0.6 自己的保留策略留下的那些），用户仍然可以手动删除。
- 清理不是每次上传都做：每个游戏大约一天一次，在上传之后或后台做，启动前不做。一台设备第一次上传某个游戏的那天不清理。
- 设备记录不是每次同步都重写（大约 6 小时一次，在存档传完之后写），所以别的设备看到的「它同步到哪个版本」可能旧一些。清理按看到的那个版本保留，多留一个旧版本，不会少留；真缺了包还有写后核对兜底（3.4）。
- 一台设备自己超过 60 天没同步过某个游戏，下次上传就传完整的包，不引用旧包。60 比 90 小，中间是余量。

### 5.5 启动前和退出后等多久

原则：**玩游戏不等云盘，除非确实有更新的进度要取。** 版本向量让「不等」变得安全：没等到的那一次最多成为一次分叉，会被发现、会问用户，不会悄悄覆盖。

| 时刻 | 现在（读代码得到的） | v2 |
|---|---|---|
| 启动前，云端没有新版本 | 列目录，逐个读没见过的元数据 | 列一次目录就知道，1 次请求 |
| 启动前，云端有新版本 | 同上，再下载整个 zip | 列目录、读索引、下载本机没有的包 |
| 启动前，云盘没反应 | 每次请求超时（默认 8 秒），再试两次（中间等 2 秒、4 秒），然后离线启动 | 整个检查有一个时间上限（默认 10 秒），到了就启动，提示「没连上云盘，这一局结束后再同步」 |
| 下载新版本到一半 | 等到下完 | 显示进度和「先玩本机的」。选了的话，这一局和云端那份成为分叉，结束后照 5.2 问 |
| 退出后 | 包装器上传完才退出（这段时间包装器还在，Steam 里游戏还算在运行）。连不上时放进待上传队列 | 先在本机生成这个版本，放进待上传队列，再上传。10 秒内传完照常结束；传不完交给后台继续，包装器退出 |
| 上传中断 | 整个 zip 重传 | 传完的包不重传，从没传完的那个包继续 |
| 没传完就关机或休眠 | 下次同步时补传 | 一样：下次开机后台继续。别的设备在这之前玩了同一个游戏，就是一次分叉，照 5.2 问 |

- **待上传队列**（`pending/<游戏>/`）里放的是完整的版本：清单加它的内容包。版本一进队列，这台设备就算同步到了它；别的设备在它传上去之前上传了别的版本，就是一次分叉。判断「云端有没有更新的」时，队列里的版本算作这条线的一部分。0.6 留在队列里的版本保留原来的 id，它的 zip 就是它自己的内容包；版本向量在上传时补上（接在它的父版本后面）。
- 每次退出后有通知：「已同步」「正在后台上传（3.2 MB）」「没连上，稍后再传」。Steam 里的插件显示同样的状态。
- 设置里可以选「退出后总是等上传完」（要马上关机的人用）。
- 后台由谁来传：托盘程序在就交给它；不在就由一个脱离包装器的进程来传。Deck 游戏模式下这一步能不能做到还要验证（第 15 节）。
- 10 秒是初始值，属于策略（3.9）。

**已经做了的**（2026-11-26，`sync.rs`、`crates/runner`、托盘程序的 `watcher.rs`）：

- **不等了的同步不会再动存档**（`sync::Gate`）。等的一方可以随时放弃（`give_up()`）；放弃之后这次同步不再发新的请求，结果是 `Outcome::Offline`。「有没有放弃」和「开始替换存档文件」是同一步：已经开始替换时放弃不了（`give_up()` 返回 `false`），等它替换完，这一步在本机，很快。已经进了队列的版本留在队列里，正在传的那个可以传完（先传包、最后写清单，传一半不会是半个版本）。`Gate` 还给出这次同步在做什么：检查、下载（已下载 / 总共多少字节，按内容包计）、替换、上传、完成。
- **启动前**：包装器在单独的线程里同步，最多等 `launch_wait_secs`（默认 10 秒）。到时还在检查、等别的同步或上传：不再等，原因记在游戏的 `last_error`，直接启动，不弹窗；结束后照常同步，没等到的那次最多是一次分叉，下次启动时问。到时正在下载更新的版本：继续下载，同时打开提问窗口（`ludonimbus-app --prompt`，不阻塞，`prompt::open_window`），写着正在下载、多大，一个按钮「先玩本机的」（B 键、关掉窗口也算）。按了就不等；先下完的话窗口自动关掉，照常继续。窗口打不开（找不到程序）就一直等下载。冲突里选了一边之后的那次同步也走同样的流程。
- 启动前只在**没连上云盘**（`Offline`）时重试，`Queued`（云端还是 0.6 的格式，游戏结束后再升级）不重试；重试的时间算在等待时间里。
- 云端还是 0.6 的格式时，启动前在冲突里选「用云端的」也不会在开游戏前升级云端（`make_current` 带上了「马上要启动」）。
- **退出后**：同步在单独的线程里，最多等 `exit_wait_secs`（默认 10 秒）；`wait_for_upload`（「退出后总是等上传完」）打开时一直等。没传完就交出去：写一个记号 `owed/<游戏>.json`（「这个游戏欠一次退出后的同步」），托盘程序在就交给它；不在就启动 `ludonimbus-run --finish <游戏>`：Windows 上用 `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP | CREATE_BREAKAWAY_FROM_JOB`，不能脱离作业时去掉最后一项再试；Linux 上用 `systemd-run --user --collect`，没有的话不交出去，照旧等传完（不然 Steam 的 reaper 反正也会让游戏一直显示在运行）。然后包装器退出，传到一半被打断不要紧，版本还在队列里。
- **谁来补**：`sync::finish_owed` 跑一次普通的退出后同步；结果是最终的（传完、已是最新、拉取、冲突已记下、没有存档）就删掉记号，连不上就留着。任何一次结果最终的同步都会删掉这个游戏的记号。这个游戏又在启动前或在玩时不补，留给这一局结束后的同步。`--finish` 不弹窗，大约 10 分钟内按越来越长的间隔重试，冲突只记下，下次启动时问。托盘程序：发现新的记号马上补；另外启动 10 秒后看一次，之后每分钟看一次 `pending/` 并上传（`sync::flush_pending`），连不上时间隔翻倍，最多 5 分钟；正在运行、正在同步的游戏跳过。补完发 `sync-finished`，界面刷新。
- **一个游戏同一时间只有一个同步**，跨进程（包装器、`--finish`、托盘程序、命令行）：`locks/sync-<游戏>.lock`，读、判断、写一条存档线的操作都先拿它（`sync`、`backup_now`、`restore`、`apply_external`、`use_line`、`flush_pending`、`upload_pending`、`finish_owed`）。锁文件记着持有者的进程 id 和它的启动时间：持有者不在了马上接手，在的话一直等，不再 30 秒就强拆（`lockfile::FileLock::hold`）。启动前等锁的时间算在等待时间里，没等到就当作没连上云盘，直接启动。
- 设置：`launch_wait_secs`、`exit_wait_secs`、`wait_for_upload`，界面里还没有开关（界面在 10.5 一起重做）。

**和上面的计划不一样的地方**：

- 启动前没连上时没有提示「没连上云盘，这一局结束后再同步」，只记在 `last_error`：规则是除了覆盖和删除不弹窗（10.1），开游戏前更不该多一个窗口。
- 下载的窗口只显示总大小，不显示进度：提问窗口是另一个进程，只在打开时读一次问题。进度在 `Gate::phase` 里有，以后的界面可以用。
- 退出后的通知（「已同步」「正在后台上传」「没连上，稍后再传」）还没做，Steam 插件里也还没有这几个状态。
- 后台上传由托盘程序或 `--finish` 进程做，不经过 `crates/agent`。
- 交出去之后，这一局的成就上传和截图（没有托盘程序时）也由接手的一方做：留在包装器里，它就还要多等几次请求。

### 5.6 每个操作的开销

| 操作 | 请求数 | 传输量 |
|---|---|---|
| 启动前检查，没有新版本 | 1（列目录） | 0 |
| 启动前检查，有新版本 | 3（列目录、读索引、读那个版本的清单），加每个要下载的包 1 次 | 本机没有的包 |
| 一台设备第一次看一个游戏 | 5：读 `format.json`、列 `library/`、读游戏记录、列目录、读索引。前两个每台设备隔一段时间才做一次，游戏记录读过就记在本机 | 几十 KB |
| 看一个云端还没有记录的游戏（没上传过） | 2：列 `library/`、列 `games/<文件夹>`。文件夹是空的就不再读存档线 | 0 |
| 退出后上传（小存档） | 4：列目录、传包、写清单、写索引。比现在多一次写索引，在后台做 | 压缩后的整个存档（不超过 16 MB） |
| 退出后上传（大存档） | 4 加每个新包 1 次，引用了旧包时再加 1 次（写完清单后列一次 `packs/` 核对） | 只有变化的文件 |
| 一个游戏第一次上传 | 上面的之外，游戏记录读 1 次、写 1 次 | |
| 打开游戏页 | 每条存档线 2 | 几十 KB |
| 刷新游戏库 | 1（列 `library/`），加有变化的记录各 1 | |
| 改一条游戏记录 | 2（写之前重读一次） | |
| 设为当前（恢复、复制） | 小存档同「退出后上传」；大存档只写清单和索引 | 小存档一个包；大存档 0 |
| 保留 | 1；改名 2（先读原来的） | |
| 删除到「最近删除」、放回 | 各 3（读、写、删） | |
| 清理（约一天一次） | 每条线列一次目录和一次「最近删除」，每个游戏列一次 `packs/`，每删一个文件 1 次；要删包时把各条线再列一次 | |

- 迁移过来的游戏，旧文件夹里有快照的，启动前检查多列一次旧文件夹（12.3）。所有设备都升级之后可以不再列它（旧文件夹不会再变），这一步放在阶段 D。升级时旧文件夹是空的游戏、升级之后才添加的游戏，存档线只有一个文件夹，不多这一次。
- 一条线有几个文件夹时，改名、放回、彻底删除要按顺序在各个文件夹里找，各多 1 次读。打开「最近删除」：每个文件夹的「最近删除」列 1 次；里面有记录时再列一次所在的文件夹，每条记录读 1 次。
- 一次操作里游戏记录只列一次（一分钟内不重列），所以刷新整个游戏库的状态是「列一次 `library/`，每个游戏列一次目录」。
- 存档线在哪些文件夹，设备记在本机，启动前不问。要写的设备每天重看一次游戏记录；只读的设备每天在退出后重看一次（多 1 次列目录），这样几个游戏并成一张卡、或者线上多了一个文件夹，它最晚一天后知道。
- 独立存档（第 7 节）的开销和共用线一样：启动前 1 次列目录。改成独立的那一次：列一次原来的线、列一次 `library/`、写一次游戏记录，然后是一次普通的上传。自己的线还没上传过任何版本时，检查只列 `library/`，不读存档线。
- **读过的小文件不再请求**：目录列表给出每个文件的变化标记，标记没变就用本机存的那份（`cloud/cached.rs`，沿用 0.6 的本机缓存文件，升级后不用重读）。清单、游戏记录、设备记录、pin、「最近删除」的记录都走这一层。
- 百度网盘每写一个文件至少 3 个请求（预创建、分片、合并），上表里的「写」在百度上乘 3。

**对照实测**（[plan-phase3.md](plan-phase3.md) E0，夸克经本机 OpenList；上传速度是当时的上行带宽，不是云盘的上限）：每个小请求 1 到 7 秒；上传 10 MB 用了 47 秒（212 KB/s）；下载 10 MB 用了 2.7 秒。

| 场景（按上面的速度估算，没有实测） | 现在 | v2 |
|---|---|---|
| 在另一台设备上玩了 20 局再回来，启动前 | 列目录 + 20 次读元数据，约 20 到 140 秒 | 列目录 + 读索引 + 下载一个包 |
| 5 MB 的存档，退出后 | 包装器等上传完，约 25 秒加几次小请求 | 上传量一样；超过 10 秒的部分在后台 |
| 500 MB 的存档文件夹（50 个 10 MB 的文件，每局新增 1 个），退出后 | 每次传整个 zip，约 40 分钟（不算压缩） | 传 10 MB，约 47 秒 |

这张表里的请求数写成了测试（`crates/core/tests/sync_v2.rs`）：用一个记下每次请求的 `Store` 跑同步流程，启动前检查、退出后上传、新设备拉取、没有记录的游戏这几项逐条比对，多出一次请求测试就失败。

## 6. 加入存档线：默认自动

一个新安装（或者扫描出来的游戏）出现时，先按 `ids` 找到游戏，再决定它跟哪条存档线：

| 档 | 条件 | 行为 |
|---|---|---|
| **直接共用** | 同一平台同一规则；Switch 本机和 Switch 模拟器；规则里这对平台标了「已实测」 | 加入这条线，不问 |
| **问一次** | 推断为同一格式：同一个 Ludusavi 标题的 Steam / Epic / GOG / Xbox 版；规则有但没标「已实测」 | 加入这条线。第一次要把别的平台的进度写进本机（或反过来）时问一次，同时给出文件对应关系的预览；确认后不再问 |
| **各自一条线** | 规则写明不通用；不同主机又没有规则 | 同一张卡，另开一条线 |

- 「问一次」时的文件对应关系，就是现在 `transfer::align` 算的东西。它从每次转移时猜，变成第一次绑定时的建议，确认后存进这个安装的 `bind`。
- **写进 Xbox 版**是实验性的（Xbox 应用的云同步可能把它换回去，见 plan-phase5 5.5），在实测够多之前每次都问，不算在「问一次」里。从 Xbox 版读出来按上表。
- 用户在「问一次」里选「不是」：这个安装另开一条线。

**安全网（每一档都有）**

1. 写之前把本机当前的存档存成恢复前版本（现有的 `protect_local`）。
2. 写完校验：按目标格式写完，再用同一个编解码读回来，内容哈希要等于要写的版本；不等就恢复并报错。
3. **撤回**：游戏页和同步后的通知里都有。恢复到恢复前版本，并且可以勾「这两个版本以后分开存」。

**高级操作**（游戏页里每个安装的菜单）：共用 / 独立（第 7 节）/ 跟随另一条线；自动同步 / 手动 / 只备份；改绑定的文件夹；拆到另一张游戏卡。

**做法**（第一步已做：`library::line_to_join`、`Cloud::record_of`、`Cloud::merge_duplicates`）

- 本机的游戏仍然用 key 命名。云端没有这个 key 的记录时，用这个游戏的强身份（`ids`）找卡；找到了，再看卡上有没有一条共用线存的正是这个版本的那些文件（格式相同、`def` 相同，3.3）。
- **有**：直接接着那条线，不建自己的记录，自己的 key 下不写存档也不写定义。属于哪条记录记在本机条目的 `record` 里（换云盘时清掉）。开销和任何一台设备第一次看一个游戏一样（列一次 `library/`、读记录、读索引），之后每次检查还是 1 次列目录。这一档现在包括：同一个 Switch 标题（本机、各模拟器）；同一条内置规则；身份相同且存档路径写法相同的 PC 版。
- **没有**（是同一个游戏，但存档在别的位置，比如另一个商店的版本、Xbox 版）：第一次上传时照常建自己的记录，随即和那张卡并成一张卡，各走各的线，互相不写对方的文件夹。之后又有设备装了这个版本，接的是这条线。
- **只是同名**：不合并，各是各的卡。用户标了「不和别的版本算同一个」（`solo:`）的条目没有强身份，同样不合并。
- **两台设备同时各建了一条记录**：下一次有设备为了写而查看游戏记录时（每个游戏每天最多一次）发现并合并。`def` 相同的线并成一份历史，两边各有进度就是一次普通的分叉，照 5.2 问；`def` 不同的各留一条线。没有重复记录时这一步不发请求。
- 每天查看记录时，顺便把这个版本知道的身份补进卡的 `ids`，以后别的版本更容易找到它。
- **从 0.6 迁移来的**两个 key 其实是一个游戏：迁移时并成一张卡，线不并（0.6 里它们就是两份历史，迁移不改变谁和谁共用）。它们的 `def` 相同的话，是否提示「可以合成一条」等界面一起定。
- **还没做**：「问一次」这一档（要有绑定和编解码，把另一个位置或另一种格式的存档对应过来）、写后校验、撤回。现在落在这一档的情况（同一个 Ludusavi 标题但存档位置不同、Steam 版和 Xbox 版）先按「各自一条线」处理，0.6 的「应用到…」照旧可用。

## 7. 独立存档（分设备存储）

同一格式下再开一条只属于某台设备的存档线（`scope: "independent"`）。

- 游戏页里这台设备选：**共用**（默认）或 **这台设备独立**。
- 独立存档可以起名字（默认是设备名）。别的设备可以选择**跟随**它。「爸爸的台式机和 Deck 共用、孩子的电脑独立」用这个就够了，不用再加「玩家」的概念。
- 设置里有设备级的默认值：「这台设备上的游戏默认独立」。
- **从共用改成独立**：新开一条线，第一个版本是本机现在的存档（`origin` 指向共用线当时的版本）；共用线不动。大存档只多一份清单，内容不重传（3.4）。
- **从独立改回共用**：和第一次加入一样，本机和共用线的最新版本不同就问留哪个，另一方留作恢复前版本。
- 独立存档之间、独立和共用之间格式相同，可以把一边的存档设为另一边的当前进度，不需要转换（第 9 节）。
- 时长和成就本来就按设备记，游戏页里独立存档的设备单独一行。

**做法**（`sync::lines`、`sync::use_line`；命令行是 `ludonimbus lines <游戏>`）

- **一台设备对一个游戏只有一条自己的线。** 线的 id 由设备 id 和本机的游戏 id 算出来（`solo-` 加四个字符），不用问云端就知道。改回共用以后再改成独立，回到的是原来那条线：接在它已有的历史后面，不会每切一次多出一条没人用的线。
- 这台设备选了哪条线，记在本机 `config.json` 的游戏条目里（`line`）；没有这一项就是没选过。云端的游戏记录只列出有哪些线，不记谁选了什么；各设备在哪条线上，看 `devices/<设备 id>.json`（3.5）。换线之后马上更新这份文件，所以别的设备列出来的「这条线上有哪些设备」是新的。
- **设备默认值只管这台设备上还没同步过的游戏。** 这样的游戏第一次上传时开自己的线，同时把选择写进条目，之后改默认值不影响它。打开默认值不会动已经在共用的游戏。默认独立的设备上，一个还没有存档的游戏不会去取共用线上的进度。
- **换线之前**，待上传队列里的版本先传到原来的线上；传不了（连不上云盘）就不换。原来那条线不动。
- **改成独立不问。** 自己的线接着本机现在的存档往下走；线上原来的最新版本留在历史里。本机没有存档而线上有，就取线上最新的。
- **改回共用、跟随别的设备的线**：就是一次普通的同步，本机在这条线上没有同步记录。内容相同就直接算作已同步；本机的存档是这条线上的某个旧版本，取最新的；都不是就问。
- **开销**：独立存档的启动前检查同样是 1 次列目录。开线时游戏记录写 1 次；之后和共用线一样（5.6）。
- 只列出、也只能跟随和这个游戏的共用线格式相同的线（合并过的游戏卡上可能有别的格式的线，那要先转换，第 9 节）。

## 8. 接管 Steam 云存档

### 8.1 已核实和没核实的（2026-11-25，只读看了这台电脑的 Steam）

- `userdata/<账号>/config/localconfig.vdf` 里每个游戏有 `cloud { last_sync_state }`：这台电脑上 90 个是 `synchronized`，1 个是 `changesincloud`。
- `userdata/<账号>/7/remote/sharedconfig.vdf` 的 `Steam` 段里有 `CloudEnabled "1"`，看位置是全局开关（没有切换过验证）。
- **没核实**：单个游戏的云开关存在哪里（这台电脑上没有关掉的游戏可以对照）。
- 现有代码：`steam::installed_apps` 能列出装着的 Steam 游戏；扫描（`discover.rs`）已经能判断一个游戏是不是由 Steam 云同步（`steam_cloud`）；存档位置来自 Ludusavi 的数据库；`steam::wrapper_options` 能生成 `"<包装器>" --game <id> -- %command%`（现在用在 Linux 的非 Steam 快捷方式上）。

### 8.2 三种状态

| 状态 | 做什么 | 风险 |
|---|---|---|
| **Steam 管**（默认） | 不碰。可以在游戏库里显示，也可以隐藏 | 无 |
| **只备份** | Steam 云照常开着。Ludonimbus 在游戏退出后存一份版本（现有的后台监视，`Trigger::Passive`），**从不自动往游戏里写** | 无冲突。得到版本历史和回档 |
| **Ludonimbus 管** | 关掉这个游戏的 Steam 云；启动前拉取、退出后上传，和现在的非 Steam 游戏一样 | 要保证 Steam 云确实关着 |

「只备份」里手动恢复一个旧版本是允许的，恢复前提示：Steam 下次同步可能问保留哪一份，选本机。

### 8.3 接管

1. 检查 `last_sync_state` 是 `synchronized`；不是就请用户先开一次 Steam 让它同步完。
2. 存一个锁定的版本「接管前」。
3. 引导用户在 Steam 里关掉这个游戏的云存档（属性 → 通用）。**Ludonimbus 不替用户改这个开关。**
4. 核实已经关掉，再把启动选项换成包装器（改 `localconfig.vdf` 要在 Steam 关着的时候做，沿用现有的「先关 Steam」流程；用户原来的启动选项保留在 `%command%` 后面）。
5. 每次启动前复查。发现 Steam 云又被打开：这一次不写入，退回「只备份」，提示用户。

- **批量**：「全部只备份」一键完成，没有风险。「全部接管」要求先关掉 Steam 的全局云开关，其余同上。
- **不用包装器的方式**（给带反作弊或自带启动器、包装后起不来的游戏）：后台在游戏没运行时就把云端的新版本拉下来，退出后上传。少了「启动前一定是最新」的保证，万一撞上就是一次分叉，照 5.2 问。
- **交还给 Steam**：去掉包装器，用户重新打开云存档。Steam 可能问保留哪一份，选本机。
- **路径**：Steam 自己的存档文件夹用新的根 `{steamuser}`（`<Steam>/userdata/<账号>`），每台设备各自解析，Steam 装在不同盘、Windows 和 Deck 之间都对得上。Proton 前缀里的路径用已经做好的前缀根。
- 接管以后，Steam 游戏也能用独立存档（第 7 节）。同一个 Steam 账号、不同的人在不同设备上玩，就是你说的那个场景。

## 9. 设为当前、转换和分享

**只有一个动作：把一份存档设为某条存档线的当前进度。** 游戏页上的「设为当前」和「发到…」（10.2）、回档、换平台、发到 Switch，都是它。做什么由来源决定：

| 来源 | 做什么 | `origin.how` | 要上传的 |
|---|---|---|---|
| 同一条线上的旧版本 | 生成一个内容相同的新版本，成为最新版本 | `restore` | 小存档一个包；大存档只有清单 |
| 另一条线，格式相同（独立存档之间、独立和共用之间） | 同上，写到目标线 | `copy` | 同上 |
| 另一条线，格式不同 | 用转换器转成目标格式，再写到目标线 | `convert:<转换器>` | 转换后的内容 |

- **它是云端的操作。** 这台设备没装这个游戏也能做。跟着目标线的设备各自在下次同步时取到；本机装着的话当场写入（先留恢复前版本）。
- 新版本的版本向量包含目标线当时的最新版本，所以它在所有设备上都是「最新」，不会被当成分叉。原来的最新版本还在历史里，可以再设回去。
- **同一条线上的不同平台之间不需要转换器。** 快照里存的是规范文件，写进哪个平台由那个安装的编解码决定（4.2）。用户看到的是「把 Xbox 的存档拖过来」，背后是一次普通的恢复，写进 Steam 版时用 Steam 版的绑定。
- **转换器**只用在格式不同的两条线之间：规则里声明（`convert`），代码里实现，一个游戏一个。例子：N64 模拟器的时之笛存档和 Longshot 的。没有转换器的两条线之间不能设，界面上写明原因。
- 都先预览、留恢复前版本、可以撤回；`origin` 让界面能显示「来自 Switch 的进度」，也避免两条线来回覆盖。
- **分享给好友**：导出一个 `.lnsave` 文件，就是一个完整的内容包（大存档先在本机拼成一个）加一份说明（游戏的 `ids`、格式、规则版本；设备名换成「分享」）。好友导入时按 `ids` 找到游戏，作为一个**旁支版本**放进他的存档线，不会自动变成最新版本，由他自己决定恢复。

## 10. 界面

**2026-11-26 定的方向**：现有的游戏页结构保留，和存档有关的只改两处（10.2）。整套界面按 10.1 的规则重做（10.5），和功能一起做完，随 1.0 发布。每个新功能实现时先按 10.1 把交互定好。

### 10.1 界面规则

新功能和以后的重构都按这几条：

| 规则 | 说明 |
|---|---|
| 一行说完 | 列表里每一项一行。页面上不放解释性的段落 |
| 解释放进问号 | 「这个功能是做什么的」放在标题旁边的 ?，鼠标停上去才显示 |
| 关键操作才弹窗 | 会覆盖本机存档、会删除的操作弹确认框：一句话、两个按钮。其余操作直接做，做完给一条能撤销的提示 |
| 一行一个主操作 | 每一行只有一个带文字的按钮，其余是图标（悬停显示名字）或者收进「更多」 |
| 状态用标记 | 「当前」「独立」用小标记，不用句子 |
| 不加动效 | 不做过渡和动画，状态变化直接换。软件常驻后台，界面看起来也要轻 |
| 常用的在第一层 | 切换存档、看这个游戏有哪些平台和设备，进游戏页就能做。改绑定、拆卡这类少用的放进菜单 |
| 不依赖拖动 | 拖动只是加分项。每个操作都有按钮或菜单，手柄和触屏一样能用 |

### 10.2 和存档有关的两处

游戏页的头部、操作栏、Steam 和游戏位置两块、游戏本体、其他页签都不动。

**① 版本条**（现有的「这个游戏的版本」那一行）

- 每个「平台 × 设备」一个小标记。共用同一个进度的连在一起，独立的单独放。一眼看出这个游戏在哪些平台、哪些设备上，谁和谁共用。
- 点一个标记出菜单：共用 / 独立（第 7 节）、自动同步 / 手动 / 只备份、改存档文件夹、拆到另一张卡。

**② 「版本历史」页签改成「存档」**

```
[Xbox]    昨天 22:14            DESKTOP-MAIN   3.2 MB    当前          ☆ ⋯
[Steam]   3 天前                DESKTOP-MAIN   3.1 MB    [设为当前]    ☆ ⋯
[Switch]  上周                  Switch         3.0 MB    [设为当前]    ☆ ⋯
[Steam]   ★ 第一年结束 · 10-15   DESKTOP-MAIN   2.4 MB    [设为当前]    ★ ⋯
▸ 自动存档 23
```

- **上半部分**只有几行：当前的一份；每个平台最新的一份（和当前不是同一份时才显示）；保留的存档（3.7）；别的设备的独立存档的最新一份。
- **下半部分**折叠：自动存档，照旧保留最近 20 个加每天一个。
- **每行一个主操作「设为当前」**（第 9 节）。现有的「恢复」和「应用到…」合成它：同一条线上是恢复，另一条线上格式相同是复制，格式不同是转换。不能转换时按钮不可用，悬停说明原因。
- **「保留」**（星标）：现有的「锁定」和「备注」合成它。保留的存档不会被清理，可以起名字。操作栏里现有的「备份当前存档」存出来的就是一份保留的存档。
- **更多**（⋯）：改名、导出、删除、发到…。「发到…」只在有别的存档线时出现：别的设备的独立存档、存档不通用的另一个版本。
- **确认框**只在会改本机存档时出现，沿用现有的 `ui.confirm`：要切换到哪一份、现在的存档会先保留。做完的提示里带「撤销」。
- **拖动**：把一行拖到版本条上的某个标记 = 发到那里。和「更多 → 发到…」是同一件事。

界面上关于存档只有三个词：**当前**、**保留**、**自动存档**。

### 10.3 和「默认自动」怎么合在一起（2026-11-26 已定：默认共用）

- 默认（几个平台跟同一条线）：在 Xbox 版玩完，当前的就是 Xbox 的那一份，启动 Steam 版会自动接上。列表里「Steam 最新」是你上次在 Steam 版玩到的地方；对它点「设为当前」，就是回到那里。
- 想让某个平台各走各的：在版本条里把它改成独立。存储和界面都一样，只是它的最新一份单独成一行，「设为当前」变成复制。

### 10.4 游戏卡

- 封面保持干净（封面上不放任何东西）。
- 封面下面一行：这个游戏有存档的平台的标志（程序的真实图标），本机没有安装的平台变灰；一个同步状态点。
- 本机能玩的彩色，不能玩的灰色（和现在一样）。

### 10.5 界面重构（和功能一起做，随 1.0 发布）

范围：游戏库和游戏卡、游戏页的布局、设置、首次引导、和掌机模式统一成一套结构、收藏视图（封面墙、总时长、成就、「已通关」和「已归档」的书架，对应规划书里「通关后可以删除」），以及把所有界面文字按 10.1 过一遍。

做法：先出草图定结构，再动代码。不加功能，只改怎么呈现。

## 11. 规则

留在主仓库，继续编译进程序。新规则随发版到用户手里，所以 nightly 构建值得早做（第 14 节）。

- **程序的规则**（一个模拟器、一个启动器怎么存档）：现在的 `adapters/builtin.yaml`、`emulators.yaml`、`recomplauncher.yaml`，不动。
- **游戏的规则**：新的 `rules/games/<id>.yaml`，一个游戏一个文件。`cross-saves.yaml`、`xbox-saves.yaml` 里单个游戏的条目、`achievements/` 里按存档判定的成就逐步并进来。

```yaml
id: stardew-valley
name: Stardew Valley
names: { zh-CN: 星露谷物语 }
ids: [steam:413150, nx:0100E65002BB8000, "ludusavi:Stardew Valley", xbox:ConcernedApe.StardewValleyPC]
lines:
  - id: main
    files: "*/*"                         # 挂载点 saves 里哪些文件算存档
    platforms:
      pc:     { saves: "{appdata}/StardewValley/Saves" }
      switch: { saves: "{nxsave}" }
      xbox:   { saves: { codec: wgs, naming: 1cnf } }
    version: { file: "*/SaveGameInfo", xml: gameVersion, newerOnly: true }
    info:    { title: { file: "*/SaveGameInfo", xml: farmName } }
    checked:
      pc-switch: untested                # verified 才算「直接共用」
      pc-xbox: untested
achievements: { … }                      # 可选，按存档判定的成就
```

- 每条规则带一个小的样例存档目录和自动测试（现有 `cross_saves.rs` 的做法），CI 里跑。
- 命令行加 `ludonimbus rules check <文件>`，贡献者本地就能验。
- `checked` 写清楚实测到了哪一步。只有 `verified` 的平台对才「直接共用」，其余是「问一次」。
- 贡献指南里写：加一个游戏只需要这一个文件加一个样例。

## 12. 迁移

### 12.1 做什么

第一台升级到 v2 的设备，在云端做一次（用一个带时间的锁文件防止两台设备同时做，和游戏本体备份的 `lock.json` 一个办法）：

1. 读所有 `games/<key>/game.json` 和本机的条目。
2. 每个 key 建一条游戏记录：id = key，`folders = [key]`，一条存档线，`path` 是新的 `games/<key>/saves/<线>`；旧文件夹 `games/<key>/snapshots`（布局 1）里有快照时，`also` 指向它。没有 `game.json` 的文件夹：名字用 key，存档线按 PC 游戏算。
3. 有相同强身份的记录合成**一张卡**（开发版写进云端的 `ids` 和手动关联，照着用；同一条内置规则的两个 key 也算）。**存档线不合并**：每个旧 key 在这张卡下仍是自己的一条线、自己的历史，和 0.6 一样。两个版本存的是不是同样的文件，迁移时无从知道；并线要等绑定和「问一次」（第 6 节），在阶段 C。
4. 锁定的版本和手动存的版本各写一个 `.pin.json`，写在新文件夹里（名字取备注，没有备注就空着，界面显示日期）；给每条线生成索引，旧文件夹里的快照和这些 pin 都收进去（旧文件夹里没有快照的线不写索引）。
5. 最后写 `format.json`。

每一步重做一遍结果都一样，所以中途断了重跑即可，两台设备同时做也不会出错；锁文件只是省掉第二台设备的重复工作。同一台设备上次中断留下的锁直接接管。没有游戏的新云端只做第 5 步，也不用锁。实现在 `cloud/upgrade.rs`。

**什么时候做**：v2 的程序要往布局 1 的云端**写**之前。只读不需要：迁移前就能按迁移后的样子读旧文件夹，所以启动前检查不会被迁移挡住。

- **启动前不做。** 启动前发现有东西要上传、而云端还是布局 1：这个版本先进待上传队列，游戏照常启动，这一局结束后再升级、再上传。升级要读每个游戏的旧文件夹，在慢的云盘上可能要几分钟，不能让游戏等它。
- 应用启动时在后台做一次（`cloud::upgrade_if_needed`），所以多数情况下第一次同步之前云端已经升级好了。
- 另一台设备正在升级（它的锁还没过期）：这台设备要写的版本进待上传队列，下次同步再传，和连不上云盘时一样。

**换云盘**（`cloud/migrate.rs`）：把旧云盘上的文件按原样复制过去，先内容（`packs/` 和旧文件夹里的 zip），再清单、pin 和「最近删除」的记录；索引不复制（它是缓存）。新云盘上已经有的游戏记录合并，没有的照抄。最后在新云盘上做一次上面的升级，所以从 0.6 的云盘换过来，结果和先升级再换一样。

每台设备本机做一次：`config.json` 的 `games` 转成 `installs`（`id` = 旧 key），旧文件另存为 `config.v1.json`。

**旧文件一个都不动、不搬、不删。** 例外只有用户自己的操作：删除旧文件夹里的一个版本、从「最近删除」放回，这两件事照 0.6 的做法在旧文件夹里做，0.6 的设备看到的也一致。

### 12.2 读旧快照

布局 1 的快照路径是 `<根>/<相对路径>`，大多数已经是 v2 的规范路径（`appdata/…`、`install/…`、`nxsave-…/…`）。两种要换：

- `drive-x/…`、`abs/…`：用快照里记的 `roots` 和旧的 `game.json` 认出它属于哪个存档文件夹，换成具名挂载点。
- Xbox 容器原样存的：读的时候用 `wgs` 解开。

旧快照的内容包就是它旁边的同名 zip。**v2 的新版本不引用旧文件夹里的包**：0.6 的设备还会按自己的保留策略删旧文件夹里的 zip，它不知道有人引用。所以大存档迁移后的第一个版本要完整传一次。

### 12.3 还在用旧版本的设备

- **开发版**（没发布过的 0.7 构建，只有你自己的设备上有）：换成新的构建即可，不做兼容。
- **0.6**（不认识 `format.json`）：继续往 `games/<key>/snapshots/` 写。旧文件夹里有快照的游戏，存档线一直读着旧文件夹，v2 的设备每次同步都看得到，有新快照就当作那台设备的版本收进来（它看不到升级之后的版本，所以通常是一次分叉，问用户）。0.6 的设备看不到 v2 的新版本，所以界面上提示「这台设备的 Ludonimbus 需要更新」。`devices/` 里所有近期活跃的设备都升级后，不再看旧文件夹。
- 存档线不读旧文件夹的游戏（升级时旧文件夹是空的，或者升级之后才添加的）：v2 的设备每天在上传之后看一眼旧文件夹（1 次列目录），里面有了快照就把它加进这条线的 `also`，之后同上。在这之前，0.6 的设备传上去的版本 v2 的设备看不到；最晚到下一次上传的第二天会发现，并且问用户。

### 12.4 回退

升级后发现问题：旧文件都在，装回旧版本、删掉 `format.json`、把 `config.v1.json` 改回来即可。v2 期间新写的版本旧版本看不到（清单在 `saves/`，内容在 `packs/`），需要时从 `packs/` 里的 zip 手动取。

**顺序**（每步单独提交、单独能测）：

1. `format.json` 检查。
2. Google Drive 并入 `Repo`。纯重构。
3. 游戏记录和云端迁移；读两种布局。
4. 安装和绑定；清单和内容包分开（读的一方认识 `in`，写的一方先只写完整的包）；索引；`drive-x` 换成具名挂载点。
5. 版本向量和分叉；保留策略；旧文件夹收件。
6. 加入存档线的三档；编解码（`files`、`wgs`、`nx`）；写后校验；撤回。
7. 独立存档；保留的存档；「设为当前」。
8. 启动前的时间上限；退出后限时等待和后台上传。
9. 大存档：只传变化的文件、分包续传、整理、删包。
10. 时长、成就、截图、封面按游戏；本机接口 4；插件；`nxlan`。
11. 游戏页的版本条和「存档」页签（10.2）。接口按「设为当前」「保留」「发到」这三个动作来设计。
12. `rules/games/`；转换；分享。

第 9 步可以放到后面：读的一方从一开始就认识 `in`，写的一方晚一点打开不影响格式。Steam 游戏（第 8 节）和界面重构（10.5）怎么排见第 14 节。

**测试**

- **请求数**：用一个给请求计数的 `Store` 跑每种同步流程，断言 5.6 表里的数字。以后谁把它改多了，测试会失败。
- 索引：删掉、写坏、少几条、多几条，结果都和逐个读清单一样。
- 大存档：改一个文件只传这个文件；引用的包缺了会补传完整的包；上传中断后接着传；整理和删包之后，每个保留的版本仍然能恢复出相同的文件。
- 版本向量：包含关系、求头、删掉中间版本后结果不变。
- 两台设备的流程（扩展 `sync_flow.rs`）：离线分叉会问；时钟差一天不影响；解决后分叉合上。
- 迁移：用一份 0.6 布局的云端样本（含 `drive-x` 路径、Xbox 容器、两个 key 其实是一个游戏），迁移后每个旧版本都能恢复出相同的文件。
- 跨平台加入：Steam 版加 Xbox 版（用现有的容器测试数据）、Switch 加 PC（星露谷样例）。
- 独立存档：切换两个方向；复制；跟随；设备默认值（`sync_v2.rs` 里的 `own_lines`）。
- 默认共用（`sync_join.rs`）：另一个 key 的同一个游戏接上同一条线，以及它的请求数；存档位置不同的同卡各一条线；只同名的、标了 `solo:` 的不合并；同时建的两条记录合并后分叉会问。
- 真实应用的步骤另写 `docs/testing-v1.0.md`，照旧由你实测。

## 15. 待验证

- Steam 单个游戏的云开关存在哪里（关掉一个游戏，对比 `localconfig.vdf` 和 `sharedconfig.vdf` 前后的差别）。
- `sharedconfig.vdf` 的 `CloudEnabled` 是不是全局开关（切换一次看）。
- Windows 上给 Steam 正版游戏的启动选项写 `"<包装器>" --game <id> -- %command%` 是否可行；带反作弊、带自己启动器的游戏各试一个。
- `localconfig.vdf` 里启动选项的位置，以及 Steam 关着时改它、再开 Steam 是否保留。
- 能不能用 `steam://` 链接直接打开一个游戏的属性页。
- Google Drive 改走通用实现后，首次列一个有很多版本的游戏要多久；需要的话保留文件属性作为加速。
- 百度网盘、夸克（经 OpenList）列目录给的变化标记够不够可靠：一个文件被重写后标记一定会变吗。`library/` 和 `index.json` 的缓存依赖它；不可靠的云盘上每次都读索引（多一次请求）。
- 5.6 的估算换成实测：在夸克和百度上各跑一遍计数的同步流程，记下每一步的秒数。
- Deck 游戏模式下，包装器退出后后台进程还能不能继续上传（Steam 会等它启动的进程的所有子进程）。不行的话交给 `crates/agent` 的常驻服务。现在的做法（5.5）：`systemd-run --user --collect` 起一个用户单元来传。要在真机上看：游戏模式的环境里 `systemd-run --user` 能不能用（有没有用户的 systemd 和 D-Bus）；用了以后 Steam 是不是马上把游戏显示为已停止，reaper 是不是不再等它；单元里的进程是不是真的传完了（看 `logs/runner.log` 里 `--finish` 的几行）。Flatpak 版的 Steam 里大概用不了，这时包装器照旧等传完，也要看一眼。
- Windows 上同样的事：包装器把上传交给 `ludonimbus-run --finish` 退出后，Steam 是不是马上把游戏显示为已停止；`CREATE_BREAKAWAY_FROM_JOB` 在 Steam 启动的包装器里能不能成功（日志里出现 "couldn't leave the wrapper's job" 就是不能）；不能脱离时 Steam 是不是还在等它。托盘程序在的时候：包装器退出后，托盘程序是不是在几秒内接手（日志里的 "post-exit (handed over)"）。
- 启动前「正在下载」的窗口：桌面上全屏的提问窗口合不合适；Deck 游戏模式下是不是显示在最前面，按 B 能不能选「先玩本机的」；先下完时窗口被关掉（结束进程）以后有没有留下 WebView 的进程。
- 10 秒在夸克、百度上够不够「没有新版本」的启动前检查（1 次列目录，实测每个请求 1 到 7 秒）；不够的话，没等到的那次会在游戏结束后同步，看日志里 "no answer from the cloud within" 出现得多不多。
- 16 MB、64 MB 两个数值：现在只有你这台电脑上 5 个游戏的数据（最大 6.3 MB）。发布前用几个存档大的游戏（一个文件夹里攒很多存档的、沙盒世界、模拟器的整套存档）量一下再定。
- 退出后「包装器没退出时 Steam 里游戏还算在运行」是按包装器的工作方式推的，没有专门测过上传慢的时候 Steam 界面是什么样。
- Xbox 版作为自动共用的一员时，Xbox 应用的云同步会不会把写入的存档换回去（plan-phase5 第 7 节原有的一条）。
- 3DS 模拟器存档路径里的机器 id，要不要做成编解码。
- plan-phase5 里还没实测的：Switch 上星露谷的存档根目录结构、主存档文件是不是压缩的。
