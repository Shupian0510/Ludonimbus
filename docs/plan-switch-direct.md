# Switch 直连云盘（设计 · 2026-11-28，不实现）

> **你问的**：Switch 能不能用电脑发过去的设置直接登录云盘，比 JKSV 好用（JKSV 的 Google Drive 要自己建 Google Cloud 项目、填客户端 id）。
>
> **现在**：Switch 只经局域网里的电脑备份、取回（[nx-protocol.md](nx-protocol.md)，协议 3）。电脑不开就不能备份。
>
> **本文**：两种做法、Switch 上要实现什么、凭据放在 SD 卡上安不安全、请求数、工作量、建议。

## 1. 结论

**能做，而且「设置从电脑发过去」正是比 JKSV 好用的地方：Switch 上不输入任何东西。** 但不建议在 Switch 上把存储 v2 再实现一遍（做法 A），建议做「收件箱 / 发件箱」（做法 B）：Switch 只往云盘里自己的文件夹放 zip、从电脑导出的文件夹取 zip，存档线、版本向量、索引仍然只有电脑那一套。1.0 不做，放 1.x。

## 2. 凭据怎么到 Switch 上

配对后的局域网连接已经是加密的、证书固定的，加一个接口就够了（协议 4）：

- `GET /nx/v1/cloud`：电脑回答云盘的种类和连接信息。只在电脑上打开「让这台 Switch 直连云盘」以后才回答（Switch 面板里每台 Switch 一个开关），默认关。
- **WebDAV**（坚果云、Nextcloud、群晖）：地址、用户名、密码。建议在面板里提示用应用密码（坚果云本来就是应用密码）。
- **S3**（R2、B2、MinIO、OSS）：端点、区域、桶、前缀、访问密钥。电脑没法替用户生成一把只能访问这个前缀的密钥，面板里提示用户自己建一把权限小的。
- **Google Drive**：电脑**再走一次授权**（浏览器里同一个 Ludonimbus 客户端，授权页写「给 Switch 用」），拿到一个**单独的 refresh token** 发给 Switch，连同客户端 id 和 secret（桌面应用的 secret 按 Google 的说法不算机密）。权限是 `drive.file`：只能碰 Ludonimbus 自己建的文件。单独的 token 可以单独撤销，不影响电脑。设备码登录（手机上点一下）也许可行，但 Google 对设备码流程允许的权限有限制，要核实 `drive.file` 在不在里面。
- **百度网盘、夸克**：不直连。百度要开放平台的应用签名，夸克靠网页 cookie 经电脑上的 OpenList，都不适合放到 Switch 上。继续走局域网。

## 3. 做法 A：在 Switch 上实现存储 v2

Switch 直接按 [plan-v2.md](plan-v2.md) 第 3 节读写：

| 要实现的 | 说明 |
|---|---|
| `format.json` | 布局不是 2、或者 `requires` 里有不认识的：只读 |
| 游戏记录 `library/` | 按 `nx:` 身份找卡；第一次给一个玩家备份时往记录里加一条线（写前重读合并、`rev` 加一） |
| 索引和目录 | 列一次线的目录，`index.json` 的变化标记变了才读；目录里有、索引里没有的清单单独读 |
| 版本向量 | 包含关系、算最新版本和分叉、新版本的计数（本设备分量取整条线的最大值加一） |
| 清单和内容包 | 清单最后写（提交标记）；内容包是 zip（`files/<路径>` 加 `snapshot.json`）。Switch 只写完整的包（16 MB 以下的档本来就是这样；更大的也可以，增量是写的一方的策略，不是格式） |
| 哈希 | 每个文件 blake3、内容哈希（要带一份 blake3 的 C 实现） |
| 保留、缺包标记 | 读 `pin`、跳过 `incomplete`；清理、补包仍然只由电脑做 |
| 离线队列 | SD 卡上 `pending/`，下次联网补传 |
| 设备记录 | `devices/nx-<id>.json`，只有它自己写 |

问题在长期：**存储格式从此有两份实现**（Rust 和 C++），每次扩展（3.9 节）都要两边改、两边测，判断最新版本或分叉的逻辑一旦不一致，就会错拉或漏传。转换（跨平台规则）不会放到 Switch 上，Switch 只能用同为 `nx` 格式的线。

## 4. 做法 B：收件箱和发件箱（建议）

```
Ludonimbus/
└─ consoles/nx-<Switch id>/                 只有这台 Switch 写（单设备写，3.1 节的一类）
   ├─ inbox/<title id>/<使用者 uid>/<ULID>.zip     Switch 备份的存档（和局域网上传的 zip 一样）
   └─ seen.json                                    电脑已经收进存档线的（电脑写，见下）
└─ consoles/outbox/<线 id>/<title id>.zip    电脑写：每个玩家的线最新的一份（含 snapshot.json）
```

- **备份**（A）：Switch 把 zip 传进自己的 `inbox/`，**1 个请求**（加第一次建文件夹）。zip 一进云盘就安全了。电脑下次运行时把收件箱里的 zip 按协议 3 的规则收进对应玩家的线（就是现在局域网上传走的那条路：`fork`、线键、队列），收完记进 `seen.json`，过几天删掉收件箱里的 zip。
- **状态**：Switch 读一次 `outbox/` 的目录列表（每个文件的变化标记和时间），和自己记的「上次同步」比，就知道哪个游戏「另一台 Switch 有更新的进度」。电脑不开时，别的 Switch 刚备份的还在收件箱里：Switch 也列一下别的 Switch 的收件箱（每台 1 个请求），比发件箱新的也算。
- **取回**（X）：先把自己现在的存档传进收件箱（就是留一份），再下载发件箱里的 zip 写入。电脑不开时也能从别的 Switch 的收件箱取。转换（PC 版的存档）只在电脑导出时做：电脑给第一个同步的玩家额外导出「PC 版最新的一份（已转换）」。
- **存储格式只有电脑一份实现**。Switch 端要的只是：HTTPS（带 CA 校验）、三种云盘的 列目录 / 读 / 写 / 删、zip（已经有）。
- **代价**：电脑长期不开，存档线不更新（但存档都在云端，不会丢）；版本历史、冲突判断在电脑收件时才有；`consoles/` 是新的一类文件夹，按 3.9 节归到「单设备写」，0.6 和旧版本看不见它，不影响它们。

## 5. 请求数（夸克那种慢盘不直连，这里按 WebDAV / Drive 每个请求 0.2–1 秒估）

| 操作 | 做法 A | 做法 B |
|---|---|---|
| 打开应用，50 个游戏的状态 | 列 `library/`（第一次还要读 50 条记录，之后按变化标记缓存在 SD 卡上）+ 每条线列 1 次目录 ≈ 50–100 | 列 `outbox/` 1 次 + 每台别的 Switch 的收件箱 1 次 |
| 备份一个游戏 | 列目录、传包、写清单、写索引 = 4（第一次加读写记录） | 1 |
| 取回 | 读索引、读清单、下载包 = 3，加备份 1 | 留一份 1 + 下载 1 |
| Google Drive 额外 | 路径要换成文件夹 id，第一次每层 1 次（缓存在 SD 卡上） | 同左，但只有两三层 |

## 6. Switch 上的通用部分（两种做法都要）

- **HTTPS 到公网**：现在的 `net.cpp` 只认固定的电脑证书、只读 `Content-Length`。要加：mbedTLS 的 CA 校验（带一份 Mozilla CA 包，约 200 KB）、SNI、分块传输（Google 的回复是 chunked）、重定向、保持连接（一次打开几十个请求）。
- **XML**：S3 的列目录和 WebDAV 的 PROPFIND 回 XML，要一个小的解析器（tinyxml2，zlib 许可）。
- **S3 签名**：SigV4（HMAC-SHA256，mbedTLS 有）。
- **Google**：用 refresh token 换 1 小时的 access token；Drive v3 的 `files.list`、`alt=media` 下载、multipart 上传（大于 5 MB 用 resumable）。
- **时间**：ULID 和签名要准确的时间：用 Switch 的网络时钟，偏差大时提示。
- **内存**：相册模式下内存少，包写到 SD 卡上的临时文件再传，不整个放内存。

## 7. 凭据放在 SD 卡上安全吗

- **SD 卡谁都能读**：拔卡插到电脑上、主机上任何一个自制程序。明文放 `config.json` 不行。
- **用只属于这台主机的密钥加密**：libnx 的 SPL 接口可以由主机自己的密钥派生出一把密钥（`splCryptoGenerateAesKek` 一类，要在大气层下核实可用），用它加密 SD 卡上的凭据。**拷走 SD 卡没用**；但同一台主机上别的自制程序能做同样的派生，所以**防丢卡、拷卡，不防主机上的恶意自制程序**。在说明里写清楚。
- **权限尽量小**：Drive 用 `drive.file`（只能碰 Ludonimbus 的文件）和单独的 token；WebDAV 用应用密码；S3 让用户建只能访问一个前缀的密钥。
- **撤销**：电脑面板里关掉「直连云盘」或取消配对时：Google 的那个 token 由电脑撤销（只影响这台 Switch）；WebDAV、S3 提示用户去改密码 / 删密钥（电脑做不到）。Switch 下次连上电脑时删掉本地凭据。

## 8. 工作量（一个人，含真机测试）

| 部分 | 做法 A | 做法 B |
|---|---|---|
| 公网 HTTPS（CA、chunked、重定向、保持连接） | 1 周 | 1 周 |
| WebDAV / S3（含 XML、SigV4）/ Google Drive | 2.5 周 | 2.5 周 |
| 存储 v2 读写（记录、索引、清单、包、版本向量、blake3、队列）+ 和 Rust 的一致性测试 | 3 周 | — |
| 收件箱 / 发件箱：Switch 端 + 电脑收件、导出、清理 | — | 1.5 周 |
| 电脑：协议 4（发设置）、Google 第二次授权、撤销、面板 | 0.5 周 | 0.5 周 |
| SD 卡凭据加密 | 0.5 周 | 0.5 周 |
| 真机（emuMMC）× 三种云盘 | 1 周 | 1 周 |
| **合计** | **约 8–9 周，之后每次改格式两边改** | **约 7 周，格式仍只有一份** |

做法 B 的大头也是三种云盘和 HTTPS；只做 WebDAV（加 S3 很便宜：都是 HTTPS 请求）可以先砍到约 3–4 周，Google Drive 放第二步。

## 9. 建议

1. **1.0 不做。** 1.0 的 Switch 是局域网经电脑：多台 Switch、在电脑上设置都已经有了，真机测试也只要测一条路。
2. **1.x 做做法 B，先 WebDAV 和 S3，再 Google Drive**（电脑第二次授权拿单独的 token）。百度、夸克继续走局域网。
3. 不在 Switch 上实现存储 v2（做法 A）。等格式稳定一年、确实有「电脑长期不开但要完整版本历史」的需求再评估。
4. 做之前要核实：SPL 派生密钥在大气层下可用；Google 设备码流程是否允许 `drive.file`；坚果云的 WebDAV 每分钟请求上限（官方说法是有限制）。
