# Ludonimbus 0.7 方案：掌机（草案 · 2026-11-24）

> **决定（2026-11-24）**：0.7 开始做跨平台，优先掌机。
>
> - **范围**：Windows 掌机（ROG Ally、Xbox Ally、Legion Go 等，Xbox 全屏体验）、Steam Deck（连同 Linux 基础移植）、Switch Atmosphère 的 S0（模拟器之间互通）+ S1（Switch 客户端经电脑同步）。
> - **存档库（2026-11-24 加入）**：游戏库分清「本机有游戏」和「只有存档」，在此基础上做存档在设备之间、平台之间的存储和转移（第 5 节）。V1 到 V3 在 H + W 之前做完。
> - **不在 0.7**：S2（Switch 直连云盘）放 0.8；macOS 往后放。
> - **测试**：没有掌机实机。Linux 在 WSL2 里开发，实机测试靠社区；Windows 掌机的全屏体验可以在这台电脑上开预览版测；Switch 你自己测。
>
> 细节沿用 [plan-platforms.md](plan-platforms.md)（Linux 移植第 1 节、游戏模式第 2 节、Switch 第 4 节）。本文只写 0.7 的范围、新增的两块（H 手柄界面、W Windows 掌机）和顺序。

## 1. H：手柄界面（Windows 掌机和 Deck 共用）

三种环境的共同点：一次只显示一个全屏窗口，没有鼠标键盘，只有手柄和触屏。

- Xbox 全屏体验：「一次只显示一个窗口，尽量全屏」，没有任务栏和托盘。
- Steam 大屏幕模式（掌机上常用）：从 Steam 启动的程序盖在大屏幕界面上。
- Deck 游戏模式：gamescope 只显示当前运行的那个程序。

### 1.1 应用的掌机模式

`ludonimbus-app --handheld`（或设置里「掌机模式：自动 / 开 / 关」，自动 = 检测到全屏体验、大屏幕模式或游戏模式时）：

- **全屏、大字、按手柄操作**：方向键 / 摇杆移动焦点，A 确认、B 返回、X / Y 做次要操作；触屏也能点。
- **内容**：游戏列表和同步状态 → 游戏页（立即同步、版本列表和恢复、冲突处理）→ 精简的设置（云盘状态、自动同步开关）。添加游戏、登录云盘、存档查找器这些复杂流程留在桌面界面，掌机模式里只提示「到桌面模式里做」。
- **输入**：同时支持 Web Gamepad API（WebView2 支持；WebKitGTK 待验证）和方向键 / 回车 / Esc（Steam Input 的桌面配置把手柄映射成键盘时用）。
- **不要求打字**：需要输入网址、密码的地方都不放进掌机模式；以后云盘登录用设备码（屏幕显示网址和代码，在手机上完成，见 plan-platforms 2.3）。

### 1.2 包装器的提示

现在包装器的冲突选择、出错提示都是系统对话框（[runner/main.rs:139](../crates/runner/src/main.rs) 的 `rfd::MessageDialog`）。在掌机上：对话框可能被大屏幕界面挡住，只能用鼠标点，Deck 游戏模式里还不一定显示。

改成：在掌机环境里，包装器以子进程启动 `ludonimbus-app --prompt <请求文件>`，全屏显示同样的选项（A = 用云端、X = 用本机、B = 取消），把结果写回文件后退出；包装器等它结束再继续。

- 用子进程而不是让托盘里的应用弹窗：Deck 游戏模式里只有 Steam 启动的那个进程树的窗口会被显示（子进程继承 Steam 的环境，gamescope 会把它当作游戏的窗口，待验证）；Windows 全屏体验里它是唯一的前台窗口。
- 找不到应用或启动失败时，退回现在的系统对话框。
- 桌面环境下行为不变，仍用系统对话框。
- **怎么判断是掌机环境**：Steam 从大屏幕 / 游戏模式启动时给子进程设置的环境变量（`SteamGamepadUI`、`SteamDeck`，待验证）、全屏体验是否开启（待验证）、或用户在设置里打开掌机模式。

## 2. W：Windows 掌机（ROG Ally、Xbox Ally、Legion Go 等）

### 2.1 已核实（2026-11-24）

- **全屏体验里没有托盘**。Xbox 给启动器的建议是不要依赖托盘，游戏启动后尽量少占资源。
- **开机启动的程序**：开启「启动时进入 Xbox 模式」后，开机启动项默认等到第一次切到桌面才运行；用户可以在「设置 → 应用 → 启动」里把单个程序设为在 Xbox 模式里也启动。
- **Xbox 应用**（2026 年 3 月起）可以把任意 `.exe` / `.cmd` 加进「我的游戏库」，能填启动参数。
- 全屏体验已经在所有 Windows 11 掌机上正式提供，台式机和笔记本有预览版。

### 2.2 要做的

- **不依赖托盘也能打开 Ludonimbus**：
  - 「把 Ludonimbus 加到 Steam」：一个非 Steam 快捷方式，启动 `ludonimbus-app.exe --handheld`，配好封面（复用现有的加到 Steam 和 SteamGridDB 封面代码）。
  - 「加到 Xbox 应用」：Xbox 应用手动添加的游戏存在哪里、能不能由程序写入，待验证；不行就在引导里教用户手动加一次。
- **首次引导**问一句「这是掌机吗」（能检测到全屏体验时默认选是），是的话把上面两项和掌机模式一起设好，并说明怎么让 Ludonimbus 在 Xbox 模式里也开机启动（能不能由程序设置，待验证）。
- **托盘里的应用没运行时，存档同步照常**：存档的下载和上传本来就是包装器自己做的，不靠托盘。托盘负责的其余工作（截图上传、包装器被强制结束后的补传）改成在下次应用或包装器启动时补做。
- **包装器的提示走 H**（1.2）。
- **从 Xbox 应用启动的游戏不经过 Steam**，包装器不会运行。如果 Xbox 应用的游戏库可以由程序写入，就像 Steam 快捷方式那样把它包装起来；否则先在文档里说明「要从 Steam 启动才会同步」。
- **休眠**：掌机常在游戏中途休眠，醒来后网络要几秒才恢复。上传、下载失败时按退避重试（和 D 共用）。
- **小屏幕**：桌面界面在 1280×800 和 1920×1080 + 150% 缩放下也要能用（全屏体验关闭时用户看到的还是桌面界面）。
- **Steam 大屏幕模式里的插件**：现在的 Millennium 插件改的是桌面版 Steam 的界面，能不能在大屏幕模式里运行，待验证。不能的话，大屏幕模式里靠 H（从游戏库打开 Ludonimbus），插件以后再说。

### 2.3 测试

这台电脑可以开全屏体验预览版，配一个 Xbox 手柄和 Steam 大屏幕模式，能覆盖窗口显示、手柄操作、开机启动这些流程。和真掌机的差别在休眠、触屏、小屏幕缩放，靠社区测试者（Ally / Legion Go）。

### 2.4 进度（2026-11-24）

H、W 已实现，自动测试通过，等你按 [testing-v0.7.md](testing-v0.7.md) 实测。

- **启动方式**：`ludonimbus-app --handheld` 是手柄界面，`--prompt <文件>` 是包装器的一个提示；两者都是单独的进程，不开托盘、不开本机接口、不受「只能开一个」限制，窗口全屏，关掉就退出。托盘里的应用照常运行。
- **手柄界面**（`app/src/handheld/`）：方向键 / 摇杆按位置移动高亮，A 确认、B 返回、Y 刷新或立即同步、LB / RB 切换游戏库和设置；键盘方向键、回车、Esc 也能用（Steam Input 的桌面配置）。高亮由界面自己标记，不依赖窗口有没有系统焦点（Steam 的界面叠在上面时也能看见）。内容按存档库来：一张卡一个游戏，灰色的排在后面；游戏页有立即同步、冲突选择、这个游戏的各个版本、存档版本（恢复、应用到其他版本）。桌面界面「设置 → 掌机 → 进入手柄界面」也能切过去。
- **包装器的提示**：所有提示改成同一个函数，掌机环境下启动 `ludonimbus-app --prompt` 全屏显示（A / X / B 对应各个选项），找不到应用或打不开时退回系统对话框。判断掌机环境：设置里的「启动游戏时的提示」（自动 / 总是全屏 / 总是系统对话框），自动 = Steam 给子进程设了 `SteamGamepadUI=1` 或 `SteamDeck=1`。全屏提示里没法选文件，游戏程序找不到时提示到桌面模式里设置。
- **存档库接上启动流程**：启动前同步完，如果同一个游戏的另一个版本（另一台设备、另一个平台）有更新的存档，问一句「应用后开始 / 不用」；选不用后同一个存档版本不再问。游戏页（桌面和手柄界面）也会显示这条提示。
- **没有托盘时**：包装器退出前，如果托盘里的应用没在运行，就补做它的事：被强制结束的包装器留下的游戏时间和存档上传，以及这个游戏的截图同步。
- **休眠后联网慢**：启动前同步连不上云盘时等 2 秒、4 秒各重试一次；退出后上传等 3 秒、6 秒各重试一次。
- **加到 Steam**：设置和首次引导里可以把「Ludonimbus」（`ludonimbus-app.exe --handheld`）加成 Steam 快捷方式，已有的会替换。还没有配封面。
- **认出掌机**：按固件里的厂商 / 型号（ROG Ally、ROG Xbox Ally、Legion Go、MSI Claw、Steam Deck、AYANEO、OneXPlayer、GPD 等）。认出来时首次引导多一步「这是掌机吗」：选是就打开全屏提示，给出「加到 Steam」、Xbox 应用的手动添加步骤和开机启动的设置位置。
- **还没做 / 待验证**：Xbox 应用的游戏库能不能由程序写入（现在只给手动步骤）；全屏体验是否开启能不能检测；程序能不能把自己设成「Xbox 模式里也开机启动」；Steam 快捷方式的封面。

**进度（2026-11-24，L + D）**：已实现，Windows 和 Linux（WSL2）上自动测试全部通过，等社区在 Deck / Bazzite 上实测。

- **找 Steam**：`~/.local/share/Steam`、`~/.steam/steam`、`~/.steam/root`、Flatpak、Snap；关闭 / 启动 Steam 用 `steam` 命令（没有时用 `steam.sh`）。
- **包装器挂在启动选项里**：`"<包装器>" --game <key> -- %command%`，快捷方式的程序不动，Proton 照常运行；用户原有的启动选项保留（`gamemoderun %command%` 原位不动，其余接在后面）。包装器收到 `%command%` 时用 Steam 设好的工作目录。识别 / 检查 / 修复都改成同时认程序和启动选项两种写法。「加到 Steam」在 Linux 上也这样建快捷方式。
- **包装器的位置**：应用（和后台服务）启动时把包装器复制到 `~/.config/Ludonimbus/bin/`，不放在 AppImage 里；同一个文件夹里记下应用的位置（`app-path`），包装器的全屏提示据此找到应用。
- **进程追踪**：包装器成为 child subreaper，启动器退出后游戏进程挂回包装器，等所有后代进程（包括 Proton 的 wine 进程）退出；进程名读 `/proc`，Proton 游戏还看命令行里的 `.exe` 名。Steam 的「退出游戏」发 SIGTERM 时包装器不会立刻退出，等游戏退出后照常上传。
- **Proton 里的存档路径**：程序是 `.exe`、从 Steam 快捷方式启动的游戏，`{home}` `{appdata}` `{localappdata}` `{documents}` 指向 `steamapps/compatdata/<快捷方式 id>/pfx/drive_c/users/steamuser/` 下面；Ludusavi 查存档时也加 `--wine-prefix`。
- **模拟器**：规则里加了 `match.linux`（Linux 程序名、AppImage、Flatpak 应用 ID）和 `rootsLinux`（XDG 文件夹 `{xdgconfig}` / `{xdgdata}`、Flatpak 的 `~/.var/app`），覆盖 Dolphin、Cemu、Azahar / Citra / Lime3DS、Ryujinx、yuzu 系、shadPS4、RPCS3、PCSX2、DuckStation、PPSSPP、Vita3K、RetroArch。yuzu 系在 Linux 上设置在 `~/.config/<名字>`、数据在 `~/.local/share/<名字>`，两处都会找。Linux 路径按各模拟器的文档写，没有实物核对。
- **密码**：Linux 上存到 Secret Service（KWallet、GNOME 钥匙串），没有时（游戏模式）存到只有本用户能读的 `credentials.json`（权限 0600）。
- **后台服务（D）**：`ludonimbus-agent`（`crates/agent`），不带界面：本地接口（和应用同一套协议，API 3）、被强制结束的包装器的补传、截图上传；桌面应用运行时它让开。用 `systemd --user` 运行。
- **本地接口 API 3**（应用和后台服务都支持）：同步时可以带 `resolution=cloud|local`（手柄处理冲突），新增「另一个版本有更新的存档」的查询、应用和忽略。
- **Decky 插件**（`plugin-decky/`）：快捷菜单面板显示正在玩（或最近启动）的游戏的云存档状态，立即同步、冲突二选一、另一个版本有更新的存档时应用、版本列表里恢复，全部手柄可用。后端只读 `agent.json` 转发请求。
- **安装**：`scripts/install-linux.sh` 装到家目录（只读系统也能用）：AppImage、包装器、后台服务、菜单项、systemd 用户服务；`--uninstall` 卸载。CI 新增 `linux-dev-build`：main 上每次提交生成 Linux 下载包（AppImage + 包装器 + 后台服务 + 安装脚本）和 Decky 插件 zip。
- **进度（2026-11-28，对照 OpenSave 补上的 Deck 功能）**：Decky 面板连不上时可以「启动 Ludonimbus」（经插件后端 `systemctl --user start`）；列出游戏库里的每个游戏（状态、立即同步 / 取回、冲突二选一、全部同步）；暂停 / 继续同步（[pause.rs](../crates/core/src/pause.rs)）；「保留这一份」；用 `/v1/changes` 等变化代替每 5 秒轮询，显示封面（本机接口 API 6，见 [steam-plugin.md](steam-plugin.md)）。本机存档全不见了时不上传空存档，显示「本机存档不见了」，只在用户取回或经 Steam 启动前写回。后台服务的用户服务降低优先级、尝试打开 lingering，也补传等着上传的版本。扫描和存档查找器看 `/run/media`、`/var/mnt`、`/mnt` 下的其他硬盘。桌面应用的 Flatpak 包（CI artifact，沙箱里做不到的见 [development.md](development.md)「Flatpak」）。都还没在真机上试过。
- **还没做 / 待验证**：AppImage 进正式发布流程（release.yml 还没改，另一个会话在改它）；Linux 上的自动更新；Steam 快捷方式用了 Proton 但程序不是 `.exe` 的情况（`CompatToolMapping`）；EmuDeck 的符号链接；Flatpak 版 Steam 的启动选项能不能调用家目录里的包装器（沙箱）；Millennium 插件在 Linux 桌面模式里能不能用；Decky 插件在真机上的界面。

## 4. S0 + S1：Switch

## 5. V：存档库（2026-11-24 提出）

> 你的想法：游戏库现在显示的是检测到的存档，存档不一定有游戏本体在电脑上，可能是残留的。要分清本机有游戏（彩色）和没有游戏（灰色，排在最后）。在此基础上打通存档的存储和迁移：设备 A 有时之笛的游戏和存档，设备 B 登录同一个云盘也能看到灰色的时之笛，备份过游戏本体的话还能拉下来；同一台电脑上 Xbox 版的存档能转到 Steam 版。存档以游戏为单位，随时能应用到任何平台的这个游戏，以后掌机和电脑之间也一样。

### 5.1 现在是什么样

- 游戏库的一项 = 本机的一个条目 = 云端的一个 key（`games/<key>/`）= 一套存档。
- 「同一个游戏」只靠 key 相同：从云端添加时沿用 key；Switch 游戏按 title id 认（S0 的 `adopt_cloud_key`）。
- 别的情况认不出来：Steam 版和 Xbox 版各是各的条目；Ludusavi 标题相同时，扫描会当成已经添加过。
- Ludusavi 扫到的游戏里，有不少是卸载后留下的存档，加进来以后和装着的游戏看起来一样。
- 云端有、本机没有的游戏只出现在「添加游戏 → 从云端添加」里。

### 5.2 三种状态

| 状态 | 怎么判断 | 显示 |
|---|---|---|
| 本机有游戏 | 本机条目，启动程序在。启动参数里带游戏文件的（模拟器游戏），游戏文件也要在 | 彩色 |
| 本机只有存档 | 本机条目，启动程序没设置（Ludusavi 找到的残留存档），或设置了但不在了（卸载、移动、移动硬盘没插），或游戏文件不在了 | 灰色，排在最后 |
| 只在云端 | 云端有 `game.json`，本机没有这个条目 | 灰色，排在最后（V2） |

- 灰色的游戏照样能同步、备份、看版本，只是不能启动。
- 显示选项里加「显示没有安装的游戏」（默认开），关掉就只看本机能玩的。
- 模拟器游戏的参数里没有游戏文件时（从模拟器自己的界面开游戏），先只看模拟器在不在。以后可以按 title id 查 Ryujinx、yuzu 系自己的游戏目录，判断得更准。

### 5.3 分步

**V1 本机分清（先做）**

- core `games::playable`；游戏库数据多一个 `playable`。
- 游戏库：灰色封面，排在最后。不分组时中间一条分隔线「本机没有安装 · N」；分组时排在每组最后。
- 显示选项加「显示没有安装的游戏」。
- 游戏页：灰色的游戏顶部说明为什么是灰色（没设置位置 / 不在原来的位置 / 游戏文件不在），带「自动查找」；备份过游戏本体的可以在「游戏本体」里从云端恢复。

**V2 只在云端的游戏**

- 游戏库列出云端有、本机没有的游戏：灰色，标「只在云端」，显示最后在哪台设备、什么时候同步过。云端的游戏列表在打开应用和刷新时取，记在本机，离线时显示上次的结果。
- **封面跟着游戏走**：游戏库里显示的封面、横幅、标志、图标传到 `games/<key>/art/`（走 `CloudProvider::files()`），别的设备显示同一套，不用再选。
- 点进只在云端的游戏：存档版本列表（可以导出 zip）、在哪些设备玩过、游戏时间。操作：
  - 「添加到本机」：现在的「从云端添加」。
  - 「从云端安装游戏」：备份过游戏本体时，恢复本体 → 建条目 → 修正路径 → 拉取存档（复用 `gamebackup` 的恢复和 `install::fix_paths` / `pull_saves`）。
- **本机其实装了**：只在云端的游戏，如果在本机找得到（同一个 Switch title id、RecompLauncher 装的游戏、按 Ludusavi 标题在商店和游戏文件夹里找到），卡片上提示「本机找到了这个游戏」，一键添加后变成彩色。

**V3 存档库：以游戏为单位，跨平台转移**

- **游戏身份**：`game.json` 加 `ids`，例如 `nx:0100F2C0115B6000`、`steam:1145360`、`ludusavi:Hades`、`xbox:<包名>`。有相同 id 的条目是同一个游戏。游戏库合成一张卡（任一版本本机能玩就是彩色），游戏页列出各个版本（平台）。认不出来时可以手动「这是同一个游戏」。
- **应用存档**：游戏页「应用到…」：选任意版本（任意设备、任意平台）的任一个存档版本，应用到本机的某个版本。应用前照旧先给目标存一个「恢复前」版本，可以撤回。
- **能不能直接用，分三类**：
  1. **格式相同**：Switch 不同模拟器（S0 已经共用一个 key）；同一个 PC 游戏的 Steam / Epic / GOG 版大多是同样的文件，只是位置可能不同，按存档文件夹里的相对路径对应。
  2. **Xbox（Game Pass）版**：存档在 `%LOCALAPPDATA%\Packages\<包名>\SystemAppData\wgs\`，是容器格式（`containers.index` 加 GUID 文件名的数据文件），不是游戏原本的存档文件。要先解析容器：多数游戏一个容器就是一个文件，通用规则就够；少数游戏要单独写规则（放进规则文件）。**读出来**（Xbox → Steam）风险低；**写进去**（Steam → Xbox）要新建容器、改索引，Xbox 应用的云同步还可能把它覆盖，放在后面、标实验性。
  3. **不同程序玩同一个游戏**（例如 N64 模拟器和 Longshot 的时之笛）：存档格式完全不同，只能一个游戏写一个转换器，不在这次范围里，有特别常玩的再单独加。
- **云端怎么存**：见 5.4 的 D1。

**V4 掌机**

- Windows 掌机、Steam Deck 本身就是电脑，V1 到 V3 直接适用。
- Switch：S1 把主机上的存档对应到 `nxsave-<title id>`。在 V3 里，Switch 主机就是这个游戏的又一个版本，和 Ryujinx / Eden 互通。

### 5.4 决定（2026-11-24）

- **D1 = A**：每个版本各存一套（和现在一样），跨平台靠手动「应用到…」；格式相同的版本自动共用一套（像 S0 那样）。转换出了错只影响手动应用的那一次，不会通过同步扩散。
- **D3 = B**：V1 到 V3 都在 H + W 之前做完，掌机互通的逻辑更清楚。
- **D2（Xbox）**：你提到以前手动把 Xbox 版的存档换到 Steam 版过，不是所有游戏都加密。调研结果见 5.5，按 5.5 末尾的做法来。

### 5.5 Xbox 存档调研（2026-11-24）

**两种 Xbox 游戏**

- **存普通文件的**：很多 Xbox 应用的游戏和 Steam 版一样把存档写在 `%APPDATA%`、「文档」之类的文件夹里，格式相同，就是 5.3 V3 的第 1 类，直接按相对路径对应。你以前手动替换成功的应该是这一种，或者是下面那种里一个容器对应一个文件的游戏。
- **用 Xbox 存档容器（Connected Storage）的**：存档在 `%LOCALAPPDATA%\Packages\<包名>\SystemAppData\wgs\<用户 ID>_<标题 ID>\`。**没有加密**，只是换了存法：`containers.index` 记着每个容器的名字和文件夹（GUID），每个容器文件夹里的 `container.N` 记着里面每个文件的名字和数据文件（GUID 命名、没有扩展名，内容就是原始文件）。

**开源项目**

| 项目 | 许可 | 做什么 | 对我们的用处 |
|---|---|---|---|
| [Z1ni/XGP-save-extractor](https://github.com/Z1ni/XGP-save-extractor) | MIT | Python，只读：把 46 个游戏的 Xbox 存档导出成 zip，按游戏的规则还原文件名 | 读取格式的参考；`games.json` 里每个游戏的命名规则（`1c1f` 一个容器一个文件、`1cnf`、`1cnf-folder`、Palworld、Starfield 等十几种）。带上它的版权声明后可以移植 |
| [brodrigz/XgpSaveTools](https://github.com/brodrigz/XgpSaveTools) | MIT | .NET 版的上面那个，多了「替换」：把 Steam 版的文件写进已有的 Xbox 存档位 | 写入方向的参考（只替换已有的存档位） |
| [Fr33dan/GPSaveConverter](https://github.com/Fr33dan/GPSaveConverter) | GPL-3.0 | 图形界面，双向转换 | 只看思路，不拷代码（许可不兼容 MIT） |
| [AbioticEditor 的 Game Pass 格式说明](https://christophervr.github.io/AbioticEditor/reference/game-pass-format) | — | 写进 Xbox 存档的完整步骤和每个字段的含义 | 写入按它的步骤做 |

**格式（几份资料对得上）**

- `containers.index`：版本号（14）、容器数、显示名、包名、索引时间（FILETIME，Xbox 同步拿它比新旧）、同步标志（1 = 已全部上传，2 = 已全部下载，16 = 有未解决的冲突），然后每个容器：名字、名字副本、ETag（服务器给的，不能自己编）、编号 N、状态（1 已同步、2 已修改、3 已删除、5 新建）、文件夹 GUID、时间、保留 8 字节、数据大小。
- `container.N`：固定的 4、文件数，每个文件 128 字节的名字（UTF-16）+ 云端记的数据文件 GUID + 本机的数据文件 GUID（同步完成时两个一样）。

**写入步骤**（AbioticEditor，XgpSaveTools 也是只换已有的存档位）：先整体备份 → 写一个新 GUID 的数据文件 → 写 `container.(N+1)` 指向它 → 改索引里这一项的编号、大小、时间、状态（有 ETag 的标「已修改」）→ 索引时间必须比原来的新、清掉「已全部上传」→ 删掉旧的 `container.N` 和旧数据文件。顺序是数据、清单、索引，每个都先写临时文件再替换。

**风险**：Xbox 的云同步可能把改过的存档换回云端的版本。几份资料的建议一致：改之前关掉游戏和 Xbox 应用；改完先离线进一次游戏、存一次档，再联网；联网后如果 Xbox 问保留哪一份，选本机。

**做法**

1. **读出来（Xbox → 别的版本）**：解析容器，按命名规则还原文件名，再按 V3 的相对路径对应到目标。规则文件 `adapters/xbox-saves.yaml` 移植 XGP-save-extractor 的通用规则和单个游戏的规则（附 MIT 版权声明）；不在列表里的游戏用通用规则（每个容器一个文件就用容器名，否则「容器名/文件名」），应用前的预览里能看到还原出的文件名。
2. **写进去（别的版本 → Xbox）**：按上面的写入步骤，**只替换 Xbox 版里已有的存档位**（名字对得上的容器）；对不上的文件列出来，提示先在 Xbox 版里存一次档。标「实验性」，应用前提示关掉游戏和 Xbox 应用、先离线进游戏存一次档。
3. 存普通文件的 Xbox 游戏不需要特殊处理，和 Steam / Epic / GOG 版一样。

**进度（2026-11-24）**：V1、V2、V3 已实现，自动测试通过，等你按 [testing-v0.7.md](testing-v0.7.md) 实测。

- core：`savelib`（游戏身份 `ids`、合成同一个游戏的 `families`、云端游戏列表存在本机 `cloud-games.json`、手动关联 / 分开）、`artsync`（封面、横幅、标志、图标传到 `games/<key>/art/`，只下载本机没有自己图片的种类）、`wgs`（Xbox 存档容器的读写）、`xboxsaves`（46 个游戏的命名规则）、`transfer`（应用存档的预览和执行）、`sync::apply_external`（先存「恢复前」版本，改完上传为最新版本）。`game.json` 多了 `ids` 和 `game`（旧版本会忽略这两个字段）。
- 应用：游戏库一张卡是一个游戏（几个版本合在一起，任一版本本机能玩就是彩色）；只在云端的游戏有自己的游戏页（添加到本机、从云端安装、版本历史、游戏时间）；每个游戏页顶部列出这个游戏的各个版本；每个存档版本都能「应用到…」本机的任一个游戏，应用前先看预览。
- 和上面设计不同的地方：游戏身份里加了名字（`name:` + 去掉符号的小写名字，至少 3 个字），所以 Steam 版、Xbox 版这类名字一样的条目不用 Ludusavi 标题也能自动认成同一个游戏；认错了可以「不是同一个游戏」。
- **只有存档通用的版本才合成一个游戏**（2026-11-24，你定的：Wii U 版和 Switch 版不合并）。每个版本有一个「存档格式」（`savelib::save_scope`）：PC 版本（Steam、Epic、GOG、Xbox 应用、手动添加）是 `pc`；模拟器按它模拟的主机（Ryujinx、Eden 等和 Switch 本机都是 `switch`，Cemu 是 `wiiu`；RetroArch 一个规则管多个主机，按它自己）；重编译 / 移植版各是各的。名字身份带上格式（`name:pc:celeste`、`name:switch:…`），Ludusavi 标题只用于 PC 版本，所以同名的跨平台版本不再自动合并。手动关联仍然可以把任何版本合在一起；这样合起来的跨平台版本「应用到…」时会提醒存档格式不同（`Plan::cross_platform`）。
- **Switch 本机的存档**单独一类来源「游戏主机」，分组和标签显示「Switch」（`SourceKind::Console`：没有模拟器规则、存档只在 Switch 游戏的两个路径根里）。电脑上有同一个 title id 的 Ryujinx / Eden 条目时，Switch 的上传本来就进那个条目。Xbox 容器除了看路径里的 `wgs`，也认「`containers.index` 旁边有 `<GUID>/container.N`」，自己写的存档位置也能用。
- 还没做：Starfield 存档写回 Xbox（一个存档由多个数据文件拼成，拆不回去，所以只能读出来）；One Lonely Outpost（gzip 压缩的 JSON）；Xbox 版里没有的存档位不会新建。

### 5.6 跨平台规则、存档的游戏版本、Ludonimbus 自己的记录（2026-11-24）

> 你的问题：要不要为不同平台的存档互转维护具体规则，每个存档顺带记下版本号？除了游戏文件，要不要也同步 Ludonimbus 自己的记录？目标是玩家的存档库：任何平台的存档都按游戏备份，支持的游戏能跨平台互转，游戏时间累计，不管在哪个平台、哪台设备都是同一套存档库，随时捡起来玩。

**规则分四层**

1. **不用规则**：同一个平台（`save_scope` 相同）、身份相同的版本格式相同，自动合成一个游戏（5.5 之前就是这样）。
2. **声明式规则** `adapters/cross-saves.yaml`（这次加的，`crosssaves.rs`）：存档在几个平台上是同样文件的游戏。一条规则写明：覆盖哪些版本（`ids`：`nx:` title id、`ludusavi:` 标题、`name:` 名字）、每个平台的存档文件夹（`pc: StardewValley/Saves`，`switch: "{nxsave}"` 表示 Switch 游戏的存档数据本身）、哪些文件算存档（设置文件不跟着走）、怎么从存档里读出写它的游戏版本、旧版游戏能不能读新版存档（`newerOnly`）。被覆盖的版本多一个身份 `fmt:<规则>`，所以跨平台也合成一个游戏；「应用到…」按规则把存档放进目标平台的存档文件夹，不再弹「格式不同」的警告。第一条是星露谷物语（Switch `0100E65002BB8000` ↔ PC）。
3. **要转换的**：规则引用代码里的转换器，像 `xbox-saves.yaml` 的 handler。Xbox 容器已经有了；以后遇到加密、字节序不同的游戏再加。
4. **兜底**：手动关联 + 「应用到…」，带跨平台警告（现状）。

每条规则带自动测试；`checked` 写清楚实测到了哪一步。规则是数据文件，别人也能提 PR 补充。

**存档的版本号**：每个快照（`snapshot.json`）多两个字段，旧版本 Ludonimbus 会忽略：

- `gameVersion`：写这份存档的游戏版本，按规则从存档里读（星露谷是 `SaveGameInfo` 里的 `<gameVersion>`；gzip / zlib 压缩过的也能读；几个农场取最新的）。决定能不能用：规则标了 `newerOnly`、源存档比目标现有存档新时，「应用到…」黄色提示先更新目标的游戏。Switch 客户端上传的存档由电脑打包时读出来。
- `installedVersion`：保存时这台设备上装的游戏版本（模拟器游戏的更新版本、重编译的版本、Xbox 应用包的版本、程序自己的版本），复用游戏本体备份读版本的代码。只用来显示和排查。
- 版本历史里显示「游戏 1.6.15」（没有就显示「安装的 …」）。Google Drive 的版本列表从文件描述里读这两个字段。

**Ludonimbus 自己的记录：建议同步，规则是**：游戏文件一个字节都不改，额外的信息都放在旁边的 JSON 里；旧版本忽略不认识的字段；本机的东西都能从云端重建（云端是唯一的来源）。已经有的：`games/<key>/game.json`（定义、`ids`、关联）、`snapshots/<id>.json`（现在带版本号）、`playtime/<设备>.json`、`screenshots/`、`art/`、`devices/<id>.json`。接下来建议加：

| 记录 | 用处 |
|---|---|
| 游戏级记录 `library/<游戏>.json` | 现在「同一个游戏」是每台设备按 `ids` 和关联自己算的。存一份游戏级记录（名字、封面、包含哪些版本、常玩哪个版本、备注），Switch 客户端、Deck 和以后别的客户端直接读，改名、合并只改一处 |
| 快照的来源 `origin` | 「应用到…」生成的版本记下从哪个版本的哪个快照来，不只写在备注里：能显示「来自 Switch」，也能避免两个版本来回覆盖 |
| 存档摘要 | 规则里加 `info`：农场名、游戏内日期、金钱、游戏时间等，读出来存进快照，版本历史显示成「存档卡片」，挑版本不用靠时间猜 |
| 跨版本的游戏时间 | 时间已经按设备、按版本记了；游戏页按「同一个游戏」把各版本加起来 |

**应用到只在云端的 Switch 版本**（2026-11-25 做了）：Switch 主机本身在电脑上只是「只在云端」的版本，现在也能当「应用到…」的目标，前提是规则覆盖它、规则里 Switch 的文件夹是 `{nxsave}`。做法：取它在云端最新的版本，把源存档按规则放进 `nxsave-<title id>/…` 叠上去（它原有的文件，比如设置，都留着），作为新的最新版本上传（`Trigger::Restore`，父版本是原来的最新版本，记下游戏版本）。原来的最新版本还在历史里，可以再应用回去。Switch 客户端下次同步这个游戏时看到云端有新版本，下载就行（电脑最多 30 秒后知道新版本）。对话框里「同一个游戏的其他版本」会列出它，标「只在云端」。没有规则的 Switch 游戏不行（报错说明原因）；只在云端的 PC 版也不行（不知道它在那台电脑上的文件夹，到那台电脑上应用）。

**待实测**（[testing-v0.7.md](testing-v0.7.md) V3 第 4 步）：Switch 上星露谷的存档根目录是不是直接放农场文件夹；有教程说 Switch 上的主存档文件是压缩的，要看 PC 版能不能直接读，读不了就要加一步转换。
