## 0. 一览

| 项目 | 做法 |
|---|---|
| 备份什么 | 一个文件夹（默认是游戏所在的文件夹），排除存档、缓存、日志 |
| 格式 | 整个文件夹按固定顺序串成一条字节流，用内容定义切块（FastCDC，平均 8 MB）切开，每块用 zstd 压缩，按内容的 BLAKE3 哈希命名。清单记录每个文件的哈希和每个块的哈希 |
| 增量 | 相同内容的块只存一份：更新后再备份，只上传变化的块；中断后重新备份，已上传的块自动跳过（断点续传） |
| 云端 | 当前云盘的单独前缀 `gamebackup/<游戏>/`，不在存档快照里，不受存档保留策略清理 |
| 恢复 | 并行下载、逐块校验哈希、写完再按文件哈希校验；中断后从断点继续；恢复后修正 Ludonimbus 和 Steam 快捷方式里的路径，再拉取云存档 |
| 入口 | 应用游戏详情页「游戏本体」卡片；设置页「云盘测速」；Steam 插件里本体缺失时显示「从云端安装」；本机接口；命令行 |

## 1. 测速

### 1.1 做法

`gamebackup::speedtest::run(store, opts)` 在当前云盘的根目录写随机数据（不可压缩，避免网盘「秒传」或压缩影响结果）：

| 轮次 | 内容 |
|---|---|
| 请求延迟 | 写一个小文件、读回来，重复 3 次，得到每次请求的固定开销 |
| 上传（单线程） | 默认 200 MB，每个对象 8 MB（和备份的块一样大），一个接一个上传 |
| 上传（并行） | 同样的量，默认 4 个线程同时上传 |
| 下载（单线程 / 并行） | 把上面两轮上传的对象读回来，检查大小 |
| 清理 | 删除全部测试文件；中途出错或取消也会清理。上次被强行中断留下的 `.ludonimbus-speed-*` 文件，下次测速开头删掉 |

每轮最多 90 秒，到时间就不再开始新的对象，按已完成的部分算速度（标记「到时间上限提前结束」）。这样百度网盘非会员（下载约 80 KB/s）也能几分钟测完。

结果给出最好的上传 / 下载速度、10 GB 和 50 GB 游戏的预计时间，以及结论：

| 结论 | 条件 |
|---|---|
| 适合 | 上传、下载都不低于 5 MB/s |
| 可以用，但大游戏要几个小时 | 有一个方向在 0.5 到 5 MB/s 之间 |
| 太慢 | 有一个方向低于 0.5 MB/s（10 GB 要 6 小时以上） |

入口：
- 应用「设置 → 云盘测速」：选数据量（50 / 200 / 500 MB）和并行数（2 / 4 / 8），显示进度和结果。
- 命令行 `ludonimbus speedtest [--mb 200] [--object-mb 8] [--threads 4] [--max-secs 90] [--json]`。
- 脚本 `./scripts/cloud-speedtest.ps1 [-Mb 200] [-Threads 2,4,8]`：编译命令行，用你的真实设置跑，报告写到 `%LOCALAPPDATA%\Ludonimbus-speedtest\`（不含密码和令牌）。测别的云盘时先在应用里切换过去再跑。

### 1.2 各云盘的已知限制

| 云盘 | 上传方式 | 已知限制 | 对本功能的影响 |
|---|---|---|---|
| **百度网盘** | 预创建 → 4 MB 分片 → 合并，每个文件至少 3 个请求 | **非会员下载限速**：[plan-phase2.md](plan-phase2.md) 实测 9 MB 用了约 116 秒（约 80 KB/s）。每个小请求约 1 秒 | 10 GB 要下载约 36 小时，50 GB 约一周。**恢复基本不可用**（会员不限速） |
| **夸克网盘** | 经本机 OpenList 中转（[plan-phase3.md](plan-phase3.md) 1.4），直接 PUT 到最终文件名 | 每个请求约 1 到 7 秒；实测 10 MB 上传 21 秒（约 0.5 MB/s）、下载 3.9 秒（约 2.6 MB/s）；非会员下载可能限速 | 上传 10 GB 约 6 小时，下载约 1 小时。可以用于小游戏 |
| **Google Drive** | 可续传上传，文件写完才出现 | 每个账号**每天最多上传 750 GB**；免费 15 GB（和 Gmail、相册共用）；单文件最大 5 TB | 大游戏可能一天传不完，第二天从断点继续；免费空间放不下大游戏 |
| **WebDAV** | 一次 PUT 一个对象，先传临时名再 MOVE | 标准里没有分片上传（Nextcloud 有自己的分片接口，不通用）；速度取决于服务器 | 备份的对象最大 24 MB，不需要分片 |
| **S3 兼容** | 一次 PUT（单次最大 5 GB），也支持分片上传 | 服务商按流量收费（下载通常收费），有的按请求次数收费 | 不需要分片；界面提示流量费 |
| **本地 / 同步文件夹** | 复制到临时名再改名 | 取决于磁盘、网络共享；同步客户端（OneDrive 等）还要在后台再传一遍 | 快；同步客户端的空间和速度另算 |

### 1.3 实测结果

本机（本地文件夹，release 版，64 MB × 每轮，2026-11-23）：上传单线程约 1.6 GB/s、并行约 4.5 GB/s，下载约 3.7 / 8.8 GB/s，测试文件全部删除。这只说明测速流程本身没问题。

**真实云盘需要你跑**（`./scripts/cloud-speedtest.ps1 -Threads 2,4,8`，每种云盘一次），把报告里的数字填进下表：

| 云盘 | 小文件写 / 读 | 上传 单线程 / 并行 | 下载 单线程 / 并行 | 10 GB 上传 / 下载 | 结论 |
|---|---|---|---|---|---|
| 百度网盘 | | | | | |
| 夸克网盘 | | | | | |
| Google Drive | | | | | |
| WebDAV（你的服务器） | | | | | |
| S3（如有） | | | | | |

### 1.4 结论和界面提示（测速后再确认）

- **百度网盘**：下载限速让恢复不可用。建议**允许备份，但卡片里明确警告**「非会员下载约 80 KB/s，恢复 X GB 预计要 Y 天」，并且第一次备份前必须确认一次。见第 7 节取舍 1。
- **夸克网盘**：上传慢，按测速结果给出预计时间；超过 5 GB 时提示。
- **Google Drive**：备份前比较大小和剩余空间；超过 750 GB 时提示「今天传不完，明天会从断点继续」。遇到 `uploadLimitExceeded` / `userRateLimitExceeded` 时停下来，说明原因。
- **WebDAV / S3 / 本地**：正常使用。S3 提示流量费。
- 每种云盘默认的并行数先用 4（夸克 2，因为请求都经过一个本机 OpenList），测速结果出来后再调。

## 2. 打包格式

> v0.3 改成按组件备份、全局去重、大文件单独切块，见第 8 节。块对象（2.3）和提交方式不变。

### 2.1 为什么这样切

| 方案 | 问题 |
|---|---|
| 每个版本打一个 zip | 不能去重：游戏打一个小补丁也要整个重传；大文件不能断点续传 |
| 每个文件单独上传 | 游戏常有几万个小文件，夸克、百度、Google Drive 每个请求要 0.3 到 7 秒，光请求就要几个小时 |
| 切块后再打成「包」（restic 的做法） | 要维护块到包的索引，删除旧版本要重新打包，复杂 |
| **把文件夹串成一条流，再按内容切块**（casync 的做法） | 小文件自然合并进块里，块的数量 ≈ 总大小 ÷ 平均块大小；按内容切，插入或删除数据后，后面的块边界会重新对齐，只有变化附近的块是新的 |

所以用最后一种：文件按相对路径排序后首尾相接成一条流，用 FastCDC 切块。50 GB 的游戏约 6400 个块。

### 2.2 切块

- 算法：FastCDC（2020 版，归一化切块），最小 2 MiB、平均 8 MiB、最大 24 MiB。
- gear 表用固定种子（splitmix64）生成，写在代码里，**永远不改**（改了以前的块就对不上，去重失效但不会出错）。参数写进清单，以后要换参数时按清单里的走。
- 块名 = 原始（未压缩）内容的 BLAKE3 哈希（64 位十六进制）。同一个游戏的所有版本共用一个块目录，相同的块只存一份。
- 本机实测（release，512 MB 随机数据）：平均块 9.0 MiB，切块约 1.4 GB/s，BLAKE3 约 6 GB/s。读文件的速度（NVMe 约 2 GB/s，机械硬盘约 150 MB/s）才是瓶颈。单元测试确认：在 4 MB 数据中间插入 777 字节后，新增的块不超过 3 个。

### 2.3 块对象

```text
"LNCK" 1 字节版本(1) 1 字节编码(0 = 原样, 1 = zstd) 数据
```

zstd 等级 3（本机实测类似游戏文本的数据约 400 MB/s 每线程，压到 27%）。压缩后省不到 3% 的（已经压缩过的资源包、视频）原样存，省得解压。编码写在对象里而不只写在清单里，因为同一个块可能被不同版本引用。以后要加密时用新的编码值，格式不用变。

### 2.4 清单

每个版本两个文件：

- `<版本>.manifest`：zstd 压缩的 JSON，几万个文件约几百 KB：

```jsonc
{
  "format": 1,
  "id": "01JD…",                      // ULID
  "game": "zelda64recomp",
  "name": "Zelda 64: Recompiled",
  "createdAt": "…", "deviceId": "d-…", "deviceName": "DESKTOP-MAIN", "appVersion": "0.6.0",
  "root": "D:\\Games\\Zelda64Recomp",  // 备份时的文件夹（仅供参考）
  "exe": "Zelda64Recompiled.exe",      // 相对 root；恢复后用来修正路径
  "workDir": "",                       // 相对 root，空 = exe 所在文件夹
  "chunking": { "algo": "fastcdc2020", "min": 2097152, "avg": 8388608, "max": 25165824 },
  "exclude": ["saves/**", "**/*.log", …],   // 这次实际用的排除规则
  "files": [ { "p": "assets/a.bin", "s": 1048576, "h": "<blake3>", "m": 1732300000 } ],  // 按流的顺序
  "dirs": ["mods", "saves"],           // 空文件夹和被排除内容的文件夹，恢复时建出来
  "chunks": [ { "h": "<blake3>", "s": 8401231, "z": 5120334 } ], // 按流的顺序：原始大小、存储大小
  "totalSize": 9876543210, "storedSize": 6543210987, "newBytes": 123456789
}
```

- `<版本>.json`：几百字节的摘要（时间、设备、大小、文件数、清单的 BLAKE3），**最后写，作为提交标记**。列版本只读这些小文件，没有 `.json` 的清单当作没写完。

### 2.5 排除什么

1. **存档**：用存档同步的扫描（`snapshot::scan`）找到这个游戏的实际存档文件，落在备份文件夹里的全部排除；存档规则里以备份文件夹为根的模式（如 `{install}/save/**`）也换算成相对模式排除。恢复后再从云存档拉取。
2. **默认排除**（保守，只排除肯定能重建的）：`**/*.log`、`**/*.dmp`、`**/*.tmp`、`**/crashdumps/**`、`**/shadercache/**`、`**/shader_cache/**`、`**/ShaderCache/**`、`**/__pycache__/**`、`Thumbs.db`、`desktop.ini`。不排除名为 `cache` 的文件夹：有的游戏把必需的数据放在叫 cache 的文件夹里。
3. 卡片里可以加自己的排除规则（glob），随清单保存，下次备份默认沿用。
4. 符号链接和目录联接不跟进（记录跳过的数量）。

被排除内容所在的文件夹仍然记在 `dirs` 里，恢复时建成空文件夹，免得游戏因为文件夹不存在而出错。

### 2.6 云端布局

```text
<root>/gamebackup/<游戏 key>/chunks/<blake3>            块（所有版本共用）
<root>/gamebackup/<游戏 key>/versions/<ULID>.manifest   清单
<root>/gamebackup/<游戏 key>/versions/<ULID>.json       摘要（提交标记）
<root>/gamebackup/<游戏 key>/lock.json                  正在备份 / 清理的设备和过期时间
```

- 建在 `Store` 之上（`crates/core/src/cloud/store.rs`）：本功能的函数都接收 `&dyn Store`，调用处传 `provider.files()`。`CloudProvider::files()` 是主会话在 `main` 上加的通用接口（存档以外的数据都走它），Google Drive 直接实现 `Store`，所以六种云盘都能用。
- 前缀 `gamebackup/` 放在根目录，不放在 `games/<key>/` 下面：主会话用 `games/<key>/playtime/`、`games/<key>/screenshots/`，而且以后按游戏复制或列出 `games/<key>/` 的代码不会碰到几十 GB 的备份。
- 和存档完全分开：不在 `games/<key>/snapshots/` 里，存档的版本列表、保留策略清理、「从旧云盘复制存档」都看不到它。
- 块放在一个文件夹里不分子目录：分 256 个子目录在夸克、百度上要多建 256 个文件夹（夸克每个约 2 到 5 秒），列出已有块也要 256 次请求；一个文件夹几千个文件对这几种云盘都没问题（Google Drive 单个文件夹上限 50 万）。
- 换云盘时不复制游戏备份（太大）。以后可以加。

## 3. 流程

### 3.1 备份

1. 检查：游戏没在运行（文件可能正在改）、云盘可用、没有别的设备持有锁。
2. 扫描文件夹，套用排除规则，显示「X 个文件，Y GB」，和上一个版本比较：文件列表、大小和修改时间（精确到纳秒）都没变时直接告诉用户「没有变化」，不上传。读完文件后如果每个文件的哈希都和上一个版本一样（文件只是被碰过），也不提交新版本。不比较排除规则本身：规则里有「现在存在的存档文件」，新建一个存档槽就会变，但游戏没变。
3. 容量检查：剩余空间（云盘报告时）不够「新增数据的估计值」时提示；Google Drive 超过 750 GB 时提示。百度、夸克按测速结果显示预计时间（第 7 节取舍 1）。
4. 写锁（30 分钟过期，备份期间每 5 分钟续一次）。
5. 列出 `chunks/`，得到已有块的集合。
6. 一个线程按顺序读文件、切块、算哈希；已有的块跳过，新块交给 N 个工作线程压缩并上传（失败隔 2 秒、8 秒、30 秒重试，仍失败就停下）。内存里最多排队 2N 个块。
7. 全部传完后再列一次 `chunks/`，确认清单引用的块都在。
8. 写清单，最后写摘要。释放锁。

断点续传：中断后重新点「备份」，第 5 步列出的已有块会跳过，只是要重新读一遍文件（NVMe 上 50 GB 约 1 分钟，机械硬盘约 6 分钟）。

### 3.2 恢复

1. 选版本（默认最新）和目标文件夹（默认原来的位置；不存在或磁盘不够时让用户选）。目标文件夹不是空的时，恢复到里面以游戏文件夹名命名的子文件夹。
2. 检查目标磁盘剩余空间。
3. 建好所有文件夹，按清单大小预先创建文件。
4. N 个线程并行下载块，校验块的哈希，解压后按偏移写进对应文件（一个块可能跨多个小文件）。完成的块记到目标文件夹里的 `.ludonimbus-restore.json`，每 5 秒写一次；中断后再恢复同一个版本到同一个位置时跳过已完成的块。
5. 全部写完后逐个文件校验 BLAKE3，不一致的文件重新下载它所在的块；恢复修改时间；删除进度文件。
6. 修正路径：游戏的 exe、工作目录、`{install}` 指向新位置（`games::set_exe`）。Steam 快捷方式：已经经过 `ludonimbus-run` 的不用改（启动时读 Ludonimbus 的配置）；没经过的，把快捷方式的目标和起始位置改到新位置（改 `shortcuts.vdf` 前沿用现有的备份机制，需要 Steam 关闭时提示）。
7. 拉取云存档：按「立即同步」处理（`sync::sync`，自动模式）；有冲突时只提示，不自动覆盖。

### 3.3 删除旧版本和清理

1. 写锁。
2. 先删摘要（取消提交），再删清单。
3. 读剩下所有版本的清单，删除不再被引用的块。
4. 释放锁。

块被多个版本共用，所以删一个旧版本只释放它独有的块。第 7 节取舍 2 决定是否自动删。

### 3.4 并发和锁

同一个游戏同时只能有一个备份或清理（`lock.json` 记设备、开始时间、过期时间；过期的锁可以接管）。恢复只读，不加锁；但清理和恢复同时进行时，恢复可能读到刚删除的块，此时报错「这个版本已被删除」。正在恢复的游戏不会被同步，也不能从 Steam 启动（插件和 `ludonimbus-run` 都会提示）。

### 3.5 容量和配额

- 卡片显示：最新备份的总大小、云端占用（最新版本的存储大小加上其他版本各自新上传的量，是估算；准确值要列出所有块，夸克、百度上太慢，命令行 `game-backup list` 会算准确值）。
- 备份前提示新增数据量；不够时不开始。
- 百度、夸克、Google Drive 的限制按 1.4 提示。

## 8. v0.3：按组件备份（阶段 A 已实现）

v0.2 把一个文件夹整个备份。你指出：重编译游戏和模拟器游戏一般都分成「程序」（重编译程序 / 模拟器本体）和「游戏文件」，应该分开备份、标上版本号。本节是按这个思路的新设计；第 9 节是要你拍板的取舍。v0.2 还没发布、你也还没测，所以**不兼容 v0.2 的格式**，直接换成格式 2。

### 8.1 v0.2 的问题

| 问题 | 例子 |
|---|---|
| **模拟器被重复备份** | 块按游戏分开存：用同一个 Cemu 的 10 个游戏，Cemu 本体存 10 份 |
| **ROM 要么漏掉、要么多传** | ROM 在模拟器文件夹外面时只提示「不会被备份」；在里面时，每个游戏的备份都会带上**所有游戏**的 ROM |
| **能下载的程序也上传** | `fefw-recomp-0.2.7`、`Zelda64Recompiled-v1.2.2` 这种发布包在 GitHub 上随时能下载；夸克、百度上传慢，传它们最费时间。真正丢了找不回来的是 ROM、解包资源、mods、配置 |
| **看不出版本** | 版本只有时间和设备，看不出是「Cemu 2.6 + 某游戏 v1.5.0（本体 + 更新 + DLC）」 |
| **大文件每次都重读** | 判断有没有变化要重新读整个文件夹；几十 GB 的 ROM 每次都要读一遍 |

### 8.2 组件

一个游戏的备份由几个组件组成，每个组件单独记版本、单独选恢复位置：

| 组件 | 内容 | 怎么处理 |
|---|---|---|
| **程序** | 模拟器本体、重编译程序的发布包、原生移植（Ship of Harkinian 等）、RecompLauncher | 程序文件夹去掉用户数据（存档、NAND 里的游戏、着色器缓存、ROM）。记下名称、版本、官方来源。多个游戏共用时只存一份（全局去重，见 8.6）。怎么存见第 9 节取舍 1 |
| **游戏内容** | ROM / ISO / RVZ / NSP / XCI / WUA，Switch 和 Wii U 的更新、DLC，重编译需要的原版 ROM 或解包资源 | 不可替代，而且基本不变。按内容存：改名、换位置、换电脑都不用重传 |
| **配置和 mods** | 模拟器按游戏的配置和手柄设置、重编译游戏的 `mods` 文件夹、材质包 | 体积小，跟游戏一起存 |
| **固件、BIOS、密钥** | Switch 的 `prod.keys` 和固件、Wii U 的 `keys.txt`、PS3 固件等 | 模拟器运行需要，但敏感：见取舍 2 |
| 存档 | | 由存档同步负责，所有组件都排除存档 |
| 不备份 | 着色器缓存、日志、崩溃转储、临时文件 | 和 v0.2 一样 |

### 8.3 不同游戏怎么拆

| 类型 | 程序 | 游戏内容 | 配置和 mods |
|---|---|---|---|
| **模拟器游戏**（规则 `kind: emulator`） | 模拟器文件夹，去掉 `roots` 里的用户数据（如 Dolphin 的 `{install}/User` 里的存档、缓存）和 ROM 类文件（`spec::junk_excludes` 已有扩展名列表） | 启动参数里的 ROM / 光盘镜像 / 游戏文件夹（`emulators.rs` 已经能找到，`EmuGame.source`），加上规则里的 `gameFiles`（更新、DLC） | 规则里的 `gameConfig`；模拟器全局配置（手柄映射等）算在程序的「本机改动」里 |
| **重编译 / 原生移植**（自己解压的发布包） | 发布包文件夹（`relocate.dirPattern` 已经能认出 `fefw-recomp-*`） | 规则里的 `userFiles`：重编译需要的原版 ROM 或光盘镜像，或者从光盘生成的文件（有的重编译工具会用你的光盘生成游戏程序） | `mods` 文件夹、配置文件 |
| **RecompLauncher 装的** | 游戏的发布包（`library.json` 里有位置）；RecompLauncher 本身作为另一个共用程序 | 同上 | 同上 |
| **普通 PC 游戏**（绿色版） | 整个文件夹作为一个组件（和 v0.2 一样） | — | — |
| **认不出来的** | 见取舍 4 | | |

### 8.4 规则文件新增的字段

模拟器规则（`adapters/emulators.yaml`）照 `gameSaves` 的写法加三个字段，`<占位符>` 由游戏 ID 填入。以 Cemu 为例（路径写规则时逐个核对）：

```yaml
- key: cemu
  # …原有字段…
  gameFiles:                     # 游戏内容：<source> 是启动参数指向的游戏文件夹 / WUA
    default: ["<source>", "{mlc}/usr/title/0005000e/<low>/**", "{mlc}/usr/title/0005000c/<low>/**"]  # 更新、DLC
  gameConfig:
    default: ["{install}/gameProfiles/<high><low>.ini"]
  firmware: ["{install}/keys.txt"]  # 取舍 2
  release: { github: "cemu-project/Cemu", asset: "cemu-*-windows-x64.zip" }  # 官方来源（阶段 B）
```

Switch 模拟器的更新和 DLC 不一定在模拟器文件夹里：以 Ryujinx 为例，它在每个游戏的配置里记下更新和 DLC 文件的路径（`games/<标题 ID>/updates.json`、`dlc.json`），这两个列表里的文件也算游戏内容，恢复后改写成新路径（格式写代码时核对）。

重编译规则（`builtin.yaml`、`recomplauncher.yaml`）加 `userFiles`、`mods`、`release`。`recomplauncher.yaml` 是从 RecompLauncher 的目录（`pc-catalog.json`）生成的，目录里每个游戏都有 GitHub 仓库、版本号、标签和各系统的发布包文件名（2026-11-23 的目录：1969 个游戏里 1892 个有 Windows 包，其中 1871 个带 SHA-256），还写了需要用户自备什么（`needs`，如「你自己的《姆吉拉的假面》」），导入脚本直接生成 `release`。

### 8.5 版本号

| 组件 | 从哪读（按顺序） | 显示 |
|---|---|---|
| 重编译程序 | RecompLauncher 的 `library.json` / 目录；发布包文件夹名（`fefw-recomp-0.2.7` → 0.2.7）；exe 的文件版本信息 | 「fefw recomp 0.2.7」 |
| 模拟器 | exe 的文件版本信息（`GetFileVersionInfoW`）；版本文件；文件夹名 | 「Cemu 2.6」 |
| 光盘镜像 | GameCube / Wii 头部的游戏 ID 和光盘版本号；PS3 / PS4 的 `PARAM.SFO`（`APP_VER`）；Wii U 的 `meta.xml`（`title_version`）。这几种 `emulators.rs` 已经在读，加几个字段 | 「GALE01 修订 2」「v1.05」 |
| Switch | 标题 ID 已经能读；版本号从文件名里的 `[v131072]` 读（NSP 里的版本信息加密，要更多密钥才能解，先不做） | 「0100…000 v1.6.0（本体 + 更新 + 2 个 DLC）」 |
| 普通 PC 游戏 | exe 的文件版本信息；读不到就只显示备份时间 | |

卡片上一行一个组件：名称、版本、大小、上次备份时间。

### 8.6 格式 2 和云端布局

```text
gamebackup/chunks/<blake3>                       所有块，全局去重（不再按游戏分开）
gamebackup/games/<游戏>/versions/<ULID>.manifest  一个版本：几个组件，每个组件的文件列表和块
gamebackup/games/<游戏>/versions/<ULID>.json      摘要（提交标记），带各组件的名称、版本、大小
gamebackup/active/<设备>-<游戏>.json             正在备份（带过期时间）
gamebackup/cleanup.json                          正在清理（全局锁）
```

- **全局去重**：同一个模拟器、同一个 ROM，不管被几个游戏、几个版本、几台电脑用到，只存一份。
- **清理变成全局的**：删除版本后，要读所有游戏的清单才知道哪些块没人用。清理时先写 `cleanup.json`，有设备正在备份（`active/` 里有没过期的）就不清理；备份开始前看到在清理就等。个人使用很少同时发生。
- **大文件单独切块**：8 MB 以上的文件各自从头切块，块边界只和这个文件有关，所以文件改名、移动、旁边加了别的文件都不影响它的块；再按「路径 + 大小 + 修改时间」在本机缓存这个文件的块列表，没变的大文件不用重读（几十 GB 的 ROM 只在第一次读）。小文件仍然像 v0.2 那样串在一起切，免得请求太多。
- 清单里每个组件：类型、名称、版本、来源（官方仓库、标签、发布包文件名和哈希）、恢复位置的写法（复用 `{install}`、`{appdata}` 这些根目录，加 `{program}`、`{content}` 两个由用户选的位置）、文件列表、块列表。
- 块对象格式（`LNCK`）、清单的提交方式、哈希校验都不变。

### 8.7 备份

1. 按规则拆出组件，显示每个组件的名称、版本、大小，可以取消勾选不想备份的（例如 ROM 已经另外备份过）。
2. 各组件分别扫描、切块；全局已有的块跳过。
3. 程序组件：按取舍 1 处理。
4. 提交一个版本（包含这次备份的所有组件）。没变化的组件引用上一个版本的文件列表，不重读。
5. 「保留最近 2 个版本」照旧，按游戏算；清理块时看所有游戏。

### 8.8 恢复

1. 对话框分开问「程序装到哪」「游戏文件放到哪」（配置跟着程序或游戏走，按规则）。默认见取舍 3。
2. **程序已经装过就复用**：本机已有同一个模拟器（逐个文件比哈希，一致）时直接用，只恢复游戏内容和配置；版本不同时问用哪个。
3. 显示下载量：「程序：已安装，跳过；游戏内容：云端 14.2 GB；配置：云端 3 KB」，阶段 B 以后还会有「程序：从 GitHub 下载 80 MB」。
4. 恢复后改写引用这些文件的地方：游戏的程序路径和启动参数（ROM 的新路径）、Steam 快捷方式、Ryujinx 的 `updates.json` 之类（每种模拟器写在规则里）。然后拉取存档。
5. 本机还没有这个游戏（新电脑）：从「添加游戏 → 来自云端」加进来后在卡片上安装；之后可以一键加入 Steam（已有功能）。

|---|---|---|
| **A** | 格式 2：全局块存储和清理、大文件单独切块和本机缓存、多组件清单；按规则拆组件（模拟器先做 Dolphin、Cemu、Ryujinx、shadPS4、RPCS3，重编译用 `relocate` / RecompLauncher 的信息）；版本号；恢复时分开选位置、复用已装的程序、改写启动参数和快捷方式；卡片和对话框按组件显示 | 集成测试加：两个游戏共用一个模拟器时模拟器只上传一次；ROM 改名不重传；大文件没变时不重读；恢复第二个游戏时复用已装的模拟器；清理不删别的游戏在用的块 |
| **B** | 官方来源：重编译从 RecompLauncher 目录生成 `release`，GitHub 上发布的模拟器手写 `release`；恢复时能从官方下载的文件优先下载（下载后逐个文件比对备份时的哈希，一致才用，其余从云端补）；GitHub 下载不了时可以「选择已下载的 zip」 | 本地模拟 GitHub 发布页（测试服务器）；真实下载交给你 |

### 8.10 风险

| 风险 | 应对 |
|---|---|
| 模拟器的文件夹布局差别大（便携版、安装版、各分支） | 规则里的 `roots` 已经按「便携版在前、安装版在后」写；认不出来的按取舍 4 处理 |
| 国内访问 GitHub 慢或失败 | 程序默认也备份在云端（取舍 1 推荐 A），官方下载只是加速；还可以手动选已下载的 zip |
| 官方发布包被删除或重新打包 | 下载后逐个文件比对哈希，不一致就用云端的 |
| 改写模拟器的配置文件（如 `updates.json`）出错 | 改之前备份原文件，格式有单元测试；改写失败时只提示，不影响恢复出来的文件 |
| 固件和密钥的法律、隐私问题 | 默认不备份，见取舍 2 |
| 全局清理读所有清单比较慢 | 只在删除版本后做一次；清单按摘要的哈希在本机缓存 |
